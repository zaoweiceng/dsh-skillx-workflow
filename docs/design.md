# 插件设计

DSH SkillX 插件的定位是：把一次成功的 Agent 执行提取成可复用、可验证、可版本化的 SkillX 能力，并让后续调用通过黑盒契约运行。

插件运行在 DSH 内。模型、会话、工具权限、凭据、沙箱和日志都由 DSH 宿主管理。

## 模块分工

| 模块 | 文件 | 职责 |
|---|---|---|
| 插件入口 | `src/index.js` | 解析配置、注册 Web API、注册 Skill Provider 和 `capability_run` |
| 能力存储 | `src/native-store.js` | 管理目录、不可变修订、版本锁和依赖闭包 |
| 契约校验 | `src/native-contract.js` | 校验执行程序、输入 Schema 和输出 Schema |
| 提取 Agent | `src/native-agent.js` | 创建 DSH Agent，从会话证据生成或优化 SkillX |
| 提取读取 | `src/extraction-reads.js` | 当前请求视图、字段去重与请求前预算估算 |
| 草稿修改 | `src/generation-draft.js` | 按摘要校验并应用局部修改 |
| 执行服务 | `src/native-execution.js` | 在 DSH PTC 中运行能力程序，记录事件和回执 |
| 恢复服务 | `src/native-recovery.js` | 对内部失败做受限恢复，必要时安排后台维护 |
| 证据快照 | `src/snapshot.js` | 从 DSH 会话事件中提取消息、工具调用和性能证据 |
| 前端入口 | `client/index.js` | 提供 SkillX 列表、启停、提取和优化入口 |

## 数据存储

默认数据根目录为当前 DSH profile 下的 `native-workflows`。

核心数据包括：

| 数据 | 位置 | 说明 |
|---|---|---|
| 能力目录与回收元数据 | `catalog.json` | snapshot-catalog-v1：当前版本、启停、回收项、清理记录、版本序号 |
| 最新可读版本 | `skillx/<name>/`、`workflow/<name>/` | SKILL.md、manifest、JS/Python 入口、资源及 docs |
| 能力修订 | `revisions/<revisionId>/` | 不可变文件快照及私有 `.record.json` 元数据 |
| 提取任务 | `jobs/*.json` | 提取或优化任务状态 |
| 来源证据 | `jobs/*.source-<序号>.jsonl` | 被选中会话的冻结证据记录 |
| 来源索引 | `jobs/*.sources.json` | 来源文件描述、摘要和性能元数据 |
| 执行记录 | `executions/<runId>/` | header、events、receipt 和恢复结果 |
| 恢复维护 | `recovery/*.json` | 受限恢复、后台诊断和优化状态 |

最新可读目录是 catalog 的派生视图，失败时记录 layoutWarning 并在启动时重建；执行读取不可变快照。旧版散列 JSON/Markdown 在启动时迁移为目录快照。发布边界在目录事务上。生成 Agent 只能先提交候选；只有它成功完成，插件才会写入不可变修订并更新目录。

## 发现和调用

启用 skillx 时，插件向 DSH 注册一个 Skill Provider。列表阶段只返回名称和说明；模型选择能力后，Provider 返回公开契约：

- 能力名称、说明和版本。
- 输入 Schema、输出 Schema。
- 是否可执行。
- 调用方式：`capability_run`。
- 依赖版本和加载回执摘要。

实现程序、依赖正文和历史证据留在插件内部。调用方读取公开契约，并使用 `capability_run` 返回的结构化结果。

## 提取链路

规划阶段以目录中的可执行契约判断能力复用，并评估固定步骤之间的数据流、前置检查和失败传播。来源会话加载的 Skill 说明和 CLI 手册作为流程证据，支持生成可直接调用的 SkillX 与工作流。

提取只做静态格式、语法、依赖与证据引用检查，不模拟或执行业务。每个产物保存自身专属的 docs 错误指引。

```text
用户选择会话
→ 插件读取会话事件
→ 保存 JSONL 证据文件与索引
→ 创建 DSH 规划 Agent，按需读取证据
→ 保存职责、证据引用和依赖版本计划
→ 新建构建 Agent，读取计划分配的 JSONL 证据
→ 提交 SkillX 候选
→ 插件检查结构、语法、依赖、Schema 及 docs 路径
→ 静态问题交回模型局部修订；没有合适实现可跳过
→ 写入不可变版本
```

提取 Agent 的权限集中在读证据、读能力、读工具定义和提交候选上。每阶段提示词提供 JSONL 文件描述及有大小上限的完整短记录，优先交付计划引用证据；其余历史内容通过受限工具按需读取。文件中保留消息、工具结果、未完成调用和控制事件；用量元数据另存于 sources.json 供统计使用。选择性审查记录来源哈希和已完整提供或读取的记录编号，审查范围以这些记录编号为准。草稿续跑、请求上下文与局部修复的运行规则见[提取草稿与预算](operation.md#提取草稿与预算)。

## 执行链路

```text
模型发现 SkillX
→ 读取公开契约
→ 调用 capability_run
→ 插件加载能力和依赖版本闭包
→ 校验输入
→ DSH PTC 运行执行程序
→ 程序调用工具或依赖 SkillX
→ 校验输出
→ 返回输出和精简回执
```

执行程序在 DSH PTC 中运行。对话内调用保留调用方的 Agent、root call 和执行 token，遵守当前对话权限。工作台通过无 Agent 的原生工具分发直接执行，使用独立执行上下文和宿主进程权限；程序与依赖使用原生执行上下文，正常执行不创建 Agent，失败时创建恢复子 Agent。

## 恢复和维护

对话内调用执行失败后，插件先分类：

- 外部阻塞：权限、凭据、审批、用户拒绝等，直接返回给调用方。
- 内部问题：程序异常、输出不合法、依赖变化等，在当前调用预算内尝试受限恢复。
- 截止时间：停止前台业务执行，保留证据，后台维护独立继续。

受限恢复使用新的 DSH 子 Agent，沿用当前权限和执行记录处理可恢复问题。恢复完成后的独立诊断区分偶发故障和实现缺陷，仅有明确方案的缺陷进入优化。

## 版本和一致性

- 能力修订写入后不可变。
- 优化必须基于当前版本，版本冲突时拒绝发布。
- 依赖按名称和版本锁定，执行前加载完整闭包。
- 目录读取和依赖加载校验修订一致性。
- 历史执行回执记录对应执行时的观察及输出来源。

## 为什么实现为黑盒能力

黑盒契约划分模型与执行程序的上下文和责任。外层模型只负责判断是否使用能力、收集输入、消费结果；内部步骤由插件按版本执行并审计。

这种分工带来三项收益：

- 模型按需读取公开契约，减少输入 Token。
- 内部程序处理步骤和验证，调用方消费业务结果。
- 执行绑定不可变版本，证据和结果可追溯。
