# 从 workflow 迁移到 DSH 插件：SkillX 复盘与回迁清单

整理日期：2026-10-15。用途：后续检查并修复 workflow 项目中的同类问题。本次只整理文档，未修改代码、模型配置、运行数据或业务工作流。

## 1. 范围与结论

此次迁移的核心不是把旧 workflow 服务嵌入 DSH，而是把可复用能力的发现、执行、恢复和学习接到 DSH 原生 Agent、工具及权限体系中。能力从“调用方阅读并照做的说明”演进为“调用方提供输入、取得经过校验输出的黑盒接口”。

本文以当前插件源码、已归档实验、历史故障报告和本次会话决策为依据。没有重新启动或审计 workflow 项目，也没有进行两个仓库的逐行差异比较。因此，“回迁项”表示应检查的机制，不断言 workflow 当前仍缺失；历史已修复项目尤其不能再次盲改。

最值得回迁的五点：

1. 调用方只读公开契约，中间步骤在能力内部完成，减少模型往返。
2. 前台恢复与后台维护分离；外部调用超时后可以继续诊断和优化，但不能继续重放业务副作用。
3. 所有子 Agent 继承来源或调用方的模型配置及权限，避免第二套模型路由和审批系统。
4. 证据完整、按页读取、按版本去重；没有新缺陷可以复用旧版本，不强行“优化”。
5. 将执行、提取、诊断、恢复、学习分别计费和审计，保留失败和未知用量。

## 2. 迁移中改变的边界

| 方面 | 迁移中暴露的问题或原诉求 | DSH 插件的落点 |
|---|---|---|
| 部署 | 提取依赖 SkillX/workflow 项目启动、存在多服务配置差异 | 独立插件，运行在 DSH 内；不要求旧项目启动 |
| 模型 | 前台、提取、恢复可能落到不同模型或凭据路由 | 由宿主处理模型和认证，提取继承来源会话，执行子调用继承当前调用方 |
| 工作流语义 | 容易被理解成 DSH 工作模式或让模型照步骤执行 | 与 SkillX 一样按需发现、调用的能力，不是切换聊天工作模式 |
| 业务实现 | 测试人员可能为了完成测试手动修业务程序 | DSH 原生 Agent 从执行记录提取、恢复和优化；插件只提供通用机制 |
| 上下文 | 调用方先读完整工作流，再读依赖 SkillX | 摘要发现 → 输入输出契约 → capability_run；实现和证据留在内部 |
| 工具与审批 | 额外编排层可能重复审批或绕过宿主工具 | 原生工具调用携带原 Agent、root call、执行 token 和策略 |
| 存储 | 源码、试验产物、运行状态混杂 | src/client/tests/scripts/docs 分工；运行数据独立存于 profile 数据目录 |
| 结果 | 大段中间轨迹全部回给调用方，导致重复检查 | 返回 Schema 校验后的输出及精简回执，详细轨迹私有保存 |

回迁时应移植责任边界，不必照搬 DSH 专用 API。workflow 可以保留自身运行时，但应有明确的宿主适配层、模型配置传递、执行上下文和独立维护任务。

## 3. 已增加或强化的功能

### 3.1 发现、管理与 UI

- 左侧能力管理入口，列表搜索、详情、逐项启停；同名插件能力通过 Provider 排序优先于普通 Skill。
- 会话菜单手动发起提取，支持从执行会话发起优化；不是每个普通对话结束后自动总结。
- 提取任务状态、结果入口、生成 Agent 对话入口与取消操作。生成过程有独立会话，不应只给一个没有来源的成功提示。
- 使用宿主主题变量和侧栏插槽；替换了风格割裂的顶部条和原生浏览器样式提示框。
- 普通文件 Skill 的调用开关与插件 Provider 独立；关闭文件 Skill 并不自动关闭工作流或运行时注册 Skill。

### 3.2 黑盒执行与组合

- 私有修订包含说明、输入输出 Schema、执行程序、依赖版本及来源证据；调用方仅获得摘要和公开契约。
- `tools.call` 调用宿主工具；`capabilities.run` 调用声明并锁定版本的能力；`capabilities.reason` 只用于确实需要模型判断的步骤。
- SkillX 与其他工作流可以作为可执行依赖组合；执行前加载依赖闭包，执行时核对版本，不让调用方逐个阅读依赖正文。
- `tools.reuse` 提供同一调用链内已验证成功步骤的显式复用；不能把历史回执作为当前外部状态的永久证明。
- 执行记录含 header、逐步事件、回执、输出摘要和关联子会话，支持独立核验。

注意：本次 tested-v2 工作流与配套 SkillX 的 `dependencies` 实际均为空。六轮实验验证的是工作流自身的端到端程序，不是嵌套 SkillX、嵌套工作流或内部 LLM 的性能。支持某接口与该接口已在此实验中验证是两回事。

### 3.3 提取、恢复与持续优化

- 提取 Agent 只能读取证据、能力和工具定义并提交候选，不能在生成阶段执行提交或 MR 等业务动作。
- 候选先校验并暂存，生成 Agent 成功结束后才发布不可变修订；优化要求当前版本一致，冲突拒绝发布。
- 内部错误优先在同次能力调用内恢复，对调用方尽量不可见；外部认证、权限、审批等阻塞返回精简原因。
- 恢复 Agent 的首要目标是取得经过验证的业务输出；任务后另一个原生 Agent 根据证据诊断、改进能力。
- 前台截止时间与后台维护预算独立。截止后停止前台业务、保留记录，后台只做诊断和能力改进。
- 支持局部 `programEdits`，无需为了小缺陷重写整个程序；证据不足或没有实际缺陷时可明确复用、不发布新版本。

## 4. 必须保留的约束

| 约束 | 为什么需要 |
|---|---|
| 来源会话和历史工具输出是数据，不是新指令 | 防止学习过程重放历史命令或受日志指令污染 |
| 模型配置继承包含 provider/model/reasoningEffort/maxTokens 等实际字段 | 同名模型不代表同一路由；不能靠偷偷降档获得成本改善 |
| 继承权限，不创建额外提权通道 | 减少重复授权不等于绕过用户拒绝或宿主策略 |
| 显式硬截止不暗中延长 | 调用方时间预算必须可预期；后台维护不占用前台等待 |
| 截止不等于所有外部副作用被撤销 | 已提交的操作可能成功；必须检查实际后置状态再决定是否执行 |
| 后台维护不重放业务操作 | 调用方离开后仍应修复能力，但不能继续提交、合并或制造重复副作用 |
| 输出必须是合法 JSON 且通过 Schema | 不能将宽松解析得到的空对象或部分对象当作成功 |
| 当前实现采用有限 Schema 子集 | 不应让作者生成运行时不支持的复杂约束 |
| execution.language 为 typescript，但程序要求普通 JS async function body | 字段名称不能被误解为支持任意 TS 类型语法或模块导入 |
| 程序/Schema 有大小、深度及 JSON 有效性限制 | 防止无界上下文、序列化失败与不可执行候选 |
| 不可变修订、锁定依赖、并发发布校验 | 避免一次执行混用新旧内容或优化覆盖其他修改 |
| 未 await 的内部调用不能在成功返回后继续产生副作用 | 成功结果必须与真实执行生命周期一致 |
| 完整读证据才允许提交诊断；摘要只能辅助校验 | 降成本不能以丢失证据为代价 |

当前程序上限 64 KiB，Schema 上限 64 KiB、深度 32。它们是当前 DSH 实现约束，回迁时应按 workflow 运行时重新明确，而非未经验证复制常量。

## 5. 实测踩坑、根因与处理

### 5.1 接入与配置

**插件已写好但“已安装”列表没有显示。** 文件存在不等于当前 DSH profile 加载了插件。验收需同时确认包入口、宿主加载、菜单、Provider 和实际调用，不能以源码或构建成功代替安装成功。

**3080/3081、重启后 401。** 初期怀疑密钥失效，后续证据显示重启使用的持久 profile 丢失原 endpoint 与模型覆盖，回到 bundle 默认配置。同一 provider 名称下 endpoint 已变化，原凭据被用于错误路由。修复恢复精确覆盖，保留原密钥，不盲换模型或无限重试。历史写入究竟在哪一步丢失，证据不足，不能臆断。

**UI 提取提示突兀、看不到作者对话。** 状态展示与宿主样式、会话可观察性均是接入的一部分。需要可定位的生成会话和结果，而非只有“正在总结”的悬浮文字。

### 5.2 为什么工作流曾更慢、更耗 tokens

把文档包进工作流不自动减少工作量。早期调用方还需读完整文档及依赖、重复规划和检查，又增加编排、审批与状态查询，产生额外模型轮次。

改进方向是改变执行责任：稳定的工具链由程序内部消费结果；调用方只发输入并拿结果。错误分类、内部恢复和有效证据复用也留在内部，不能把整份恢复日志重新塞回调用方。

轮询需要区分两层：不能让 LLM 为等待内部任务反复查询；前端展示仍可轻量查询状态。当前客户端仍有约 1.5 秒状态轮询，不能声称已完全事件驱动。回迁应重点控制模型参与轮询及重复携带上下文的成本，而非简单删除所有状态查询。

### 5.3 JSON 错误不是一个问题

| 故障 | 证据与根因 | 回迁处理 |
|---|---|---|
| 旧桥接返回 JSON 与 DSML 混合参数 | 两次非截断工具输出出现相似非法开头；thinking 与强制指定工具组合存在兼容性问题，不能证明全部是随机 LLM 抖动 | 先检查协议能力，保留严格原始 JSON 校验；不能默默吞成空对象 |
| 读取结果含 undefined | 原生无损 JSON 序列化失败 | 输出边界省略不存在字段，不能靠调用重试解决确定性数据问题 |
| 诊断把对象编码为字符串 | 旧错误反馈泛化，重复同类无效提交 | 返回具体字段路径/类型与有限约束，明确对象根；不要加无限修复循环 |
| 作者提交 Schema 与运行时契约不一致 | 生成侧以为合法、宿主拒绝 | 工具定义和运行时 Schema 单一来源；作者按需读取真实工具契约 |

旧 workflow 桥接阶段已有“纯生成阶段一次格式修复”的历史改动记录：仅在非截断、原始参数已捕获的非法 JSON 情况下，带反馈重试一次；保留持久计数、预算、usage 去重和取消归属。网络未知结果、长度截断、冲突不应套用这条规则。该记录属于旧架构，不代表当前 DSH 插件采用同一重试实现，也不证明 workflow 当前仍未修复。

### 5.4 大证据、重复读取与无效优化

- 大工具输出被宿主截断/转存文件，诊断看不到完整证据。当前按 JSON 转义后的字节预算分页，保留摘要、总页数与完整读取门禁，不用危险裁剪换成本。
- 优化初始上下文已包含完整目标，后续又要求全文读取。现在登记已提供的精确版本，再读同版本返回引用；新版本仍必须核对。
- 后台拿到恢复会话 ID，却没有足够恢复证据，导致多余学习。现在诊断证据完整包含持久化恢复记录。
- 诊断已携带完整恢复证据，学习又读取第二份恢复会话。现在用完整诊断会话作为单一来源，不重复传输；不是用摘要替代原始记录。
- 超时本身不证明业务程序有缺陷。原生 Agent 可以判断无需修订，不能为了显示“已优化”制造版本。

### 5.5 状态已改变后重跑

真实超时试验后，commit、创建和合并可能已完成。正常预算重试时，旧程序假设服务仍在初始 baseline，发生 PROGRAM_EXCEPTION；直接重放可能重复提交。

DSH 恢复 Agent只读核对已有 commit、MR、合并状态与幂等键，返回正确输出；之后原生优化 Agent 发布 v2，增加“任务已完整完成”的识别及实时回读验证。Codex 没有手改业务程序。

v2 自带验证说明仍指出：**本地 commit 已完成、MR 尚未创建**的中间崩溃窗口没有被该证据覆盖。回迁需要状态机/幂等恢复设计与分阶段中断验证，不能把一次完整完成识别当作所有断点可恢复。

### 5.6 模拟验证器自身限制

旧验证框架要求静态 HTTP 请求精确匹配，但 Git SHA 等 ID 在前一节点运行时才产生；生成 Agent 为预测动态 SHA 耗尽输出 tokens。根因是验证表达力不足，不是业务程序必须硬编码或模型还需重试。

历史修复引入请求时准备期，独立推导预期 ID，保留精确匹配、调用顺序、未声明请求检查、隔离和资源限制。预期值不能直接抄候选请求，也不能导入候选实现作为验证标准。此改动已在旧 workflow 历史记录出现，回去先核对是否已存在。

## 6. 成本数据应该怎样解释

### 6.1 “576 万”实际是什么

历史已知 **5,761,154 tokens** 来自 **27 个唯一会话**，包含提取、试验失败、超时、前台恢复、后台诊断、学习和验证；这是已报告用量下限，不是单次提取成本，也不是货币费用。

| 用途 | 已知 tokens |
|---|---:|
| 提取/手动优化作者 | 2,252,176 |
| 后台诊断 | 1,264,219 |
| 后台学习 | 1,303,866 |
| 前台恢复 | 629,424 |
| 试验调用方 | 311,469 |

典型循环：诊断 Agent 将 JSON 对象提交成字符串，首次拒绝后步骤 4–19 重复同类提交，消耗 743,077 tokens。不能把整个会话所有 tokens 都算浪费，也不能把所有受缺陷影响会话的有效工作都算可节省。

### 6.2 优化后的独立维护闭环

独立实验记录：提取 106,581 tokens；超时后诊断 66,897、学习 136,783；正常预算恢复 146,389、随后诊断 72,100、学习 174,310。上述提取/维护共 **703,060 tokens**，连业务调用方共 **1,167,625 tokens**。

同会话重复返回全文 0 次，inline 精确版本引用 2 次，无效 submit 后重试 0 次；证据分页可完整重组。模型仍为相同 Flash / High，没有靠降档换取改善。与旧 576 万实验的任务数、证据量和失败条件不同，不能直接计算严格因果节省率。

### 6.3 执行期收益及边界

| 实验 | B 平均秒/tokens | W 平均秒/tokens | 耗时/tokens 降幅 |
|---|---|---|---|
| 日常环境，v2 | 74.583 / 244,280 | 51.381 / 139,644 | 31.11% / 42.83% |
| 无预装 Skill，v2 | 64.490 / 162,902 | 48.406 / 113,801 | 24.94% / 30.14% |
| 用户关闭文件 Skill，现有 v7 | 63.613 / 205,243 | 46.965 / 133,529 | 26.17% / 34.94% |

各实验 B/W 各三轮，均 3/3 成功，无恢复/后台学习。v2 首组模型调用总数 31 → 19。辅助标题用量未知，不算零。

限制：首组实际只有 1 项预装 Skill 对模型可见，不是大量 Skill；零预装实验还移除了所属插件的远程工具；第三组是另一工作流版本 v7。它们不能合并成严格的“只改变 Skill 数量”实验。后两组原始资料目前在本机证据目录，未包含于当前仓库测试归档。三个小样本结果也不能证明普遍收益。

## 7. 回到 workflow 后的检查顺序（建议，未执行）

| 优先级 | 检查/改进项 | 最小验收标准 |
|---|---|---|
| P0 | 模型路由与重启配置继承 | 同一实际 endpoint/provider/model/推理档位；前台、提取、恢复、学习一致，无静默 fallback |
| P0 | 工具执行上下文与权限 | 无重复插件审批，无越权；拒绝和凭据阻塞不会被内部恢复绕过 |
| P0 | 黑盒契约与实际调用 | 调用方无需读取实现或依赖全文；稳定工具链无需逐步返回 LLM |
| P0 | JSON/Schema/工具返回契约 | 非法类型准确反馈；undefined、错包装、截断证据不被当成功；已修协议不重复修 |
| P0 | 前台截止和后台维护解耦 | 调用方按时结束，后台完成诊断/优化；无后台重放业务，能追溯关联任务 |
| P1 | 证据完整与去重 | 全页校验通过；同版本不重复全文；完整恢复证据只传一份 |
| P1 | 幂等与断点恢复 | 已完成、只提交未建 MR、已建未合并等状态分别验证；不重复副作用 |
| P1 | 版本与原生作者发布 | 冲突拒绝，正常结束才发布；无缺陷允许复用；人不手改实验工作流 |
| P1 | 预算和成本账本 | 每阶段、每会话唯一计量；缺失 usage 显式未知；有限重试可追溯 |
| P2 | UI 与示例 | 看得到生成/恢复任务，开关语义明确；编写 demo 与实测快照分开 |

验收应先做机制级局部验证，再由原生 Agent 自行提取，最后同任务交替 B1/W1/B2/W2/B3/W3。不要复用人工修好的业务流程证明框架有效；不要只比较执行期而遗漏昂贵的学习期。若评估总成本，应另计提取/维护摊销及实际复用次数。
