# P0：提取结果必须可调用

## 问题与范围

历史三次开启侧调用均为零次 capability_run。静态提交成功只说明程序和 Schema 合法；计划允许把所有可复用结果收进一个 self，执行环境仅为自由文本。调用方发现宿主/容器边界不符后回退原程序，不能算复用成功。

本次改动仅涉及提取契约、正常执行的目标绑定和验收记录，不修改运行时恢复策略。不保留有缺陷的提取协议；旧产物手动停用、重新提取。不编写或运行单元测试，用隔离真实 Agent 运行验收。

## 契约

1. 提取请求可显式携带用途验收条件（最小工作流层数、独立分支、执行目标）。这些来自用户的用途，不是全局凑数规则。保存为不可被构建 Agent 修改的任务条件，校验规划与最终可执行依赖，而非注释和自述。
2. 工作流必须调用其他能力，原子 Skill 不得声明能力依赖。避免把整段原始脚本标为 workflow。深度从真实 capability 调用和版本锁推导。
3. execution.target 是宿主管理的执行目标契约。容器目标要求公开 executionTarget 输入，子调用继承同一目标，禁止悄悄退回 local。processes 与 resources 由宿主封装 docker exec 的 argv。容器内解释器、工作目录、环境和资源属于容器，不能使用宿主的解释器路径。原生工具权限检查仍执行。
4. 容器资源通过 stdin 传输至临时目录，按原始相对路径保存后运行并清理；不依赖 DSH 目录恰好被挂载。编排程序只处理 JSON 与 SDK 调用，目标内文件与第三方库操作放入资源脚本。执行目标不是完整安全沙箱声明。
5. 受管理进程遵循可执行程序的 await/Promise.all，不再要求叶子重复声明 parallel 元数据；其他原生工具仍按原有互斥顺序。实跑以时间戳与产物验证真正重叠，语法 Promise.all 不作为完成证明。

## 提取与修复

规划 Agent 按来源独立结果定义能力边界，宿主按用途条件验证。构建 Agent 实现冻结计划；宿主注入执行目标公开 Schema 并保存版本锁。校验失败回到提取草稿，不调用运行时修复掩盖契约缺失。业务行为是否正确只能通过真实调用确定，结构合法不是“可用”。验收 Agent 自行调用并根据原始失败证据修复；观察者不改候选业务程序。

## 真实验收及成本

在已有专用容器与独立 DSH 配置内重新提取。以 capability_run 回执与 implementation/start/end 证明三层嵌套；以分支时间区间、汇合产物校验并行与依赖；以失败后再次调用验证成功结果复用和失败分支重做。CLI 并发安装/中断、Python 与 JS 第三方依赖仍需真实验证。失败应明确区分环境、业务代码、输入和未知，不能强行分类。

性能使用同模型、同输入、同预热依赖、独立会话与输出目录；关闭侧原程序，开启侧只允许 capability_run。三组交错执行。统计完整调用会话和其修复子会话的 Token、活动耗时；排除提取/准备。失败或回退单列，不纳入成功均值。

## 实跑追加发现

- 资源修订的只读接口不能用“初始提示已提供”代替真实正文。初始提示只有资源摘要，首份草稿尚未提交时原来的 draft 读取也没有候选。现允许按 JSON Pointer 读取当前修订资源，draft 读取在没有候选时回到同名选中修订；仍分页、仍只读，不执行资源。
- 同样的汇总数字不等于相同的交付物。实跑发现提取后的 Parquet 曾从活动行分组摘要退化成原始明细；必须直接读取产物并与来源对照，不能把报告的 passed 当作等价证明。该批性能数据保留为无效对照，不用于最终等价比较。
