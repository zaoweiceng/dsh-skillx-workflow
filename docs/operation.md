# 运行机制

本页说明 SkillX 在插件中怎样被提取、启用、执行和优化，以及为什么启用 skillx 能减少耗时和 Token。

## 开发者使用路径

```text
完成一次代表性任务
→ 从会话菜单发起 SkillX 提取
→ 等待提取 Agent 生成候选
→ 在 SkillX 页面查看能力
→ 按需启用或停用
→ 后续任务由模型发现并调用 SkillX
→ 用新的执行会话优化能力
```

首次任务仍由 Agent 正常探索。只有当任务结构稳定、执行证据完整时，才适合提取为 SkillX。

## 证据怎样被提取

插件从 DSH 会话事件提取证据，包括：

| 证据 | 用途 |
|---|---|
| 用户消息和助手回复 | 还原任务目标、输入来源和输出要求 |
| 工具调用和结果 | 还原实际操作、参数、状态和失败点 |
| 未完成调用 | 判断中断或异常边界 |
| step 事件和用量 | 比较耗时、模型调用和 Token |
| turn 结束原因 | 判断会话是否完整完成 |
| 模型请求配置 | 保留来源模型作为证据元信息 |

提取 Agent 从历史证据总结可复用输入、必要工具、验证条件和失败边界。

证据保存在插件 `jobs/<任务 ID>.source-<序号>.jsonl`，首次提取的提示词提供文件路径、摘要哈希和记录数；续跑实现时可由宿主提供有大小上限的完整引用记录。Agent 通过受限的 `read_native_execution` 工具读取这些固定文件：先分页查看索引或按字面关键词搜索，再读取相关记录；大记录可按字符范围读取局部片段，完整详情则支持分片。预览和局部片段带有完整性标记。工具根据来源会话和记录编号读取冻结文件。

单来源与多来源均按职责选择相关证据。发布记录保留来源 JSONL 哈希及完整读取的记录编号，明确采用选择性审查。提交要求每个来源至少有一条完整记录进入构建上下文。提取先保存一个简短职责计划，再经过独立验收契约阶段，由全新 DSH Agent 在独立上下文中按计划构建。计划逐候选引用实际完整读取的 JSONL 记录，构建者必须获取对应完整证据；宿主在续跑提示词中提供的完整记录也计入已读，未提供的记录仍须通过工具读取。已有依赖在计划和构建之间锁定版本。发布时检查候选与计划一致，并通过 AST 核对依赖声明和字面名称的 capabilities.run 调用；同时进行业务语义审查和隔离执行验证。候选说明记录证据范围和验证条件。JSONL 每个文件的存储上限为 64 MiB。较大的证据按相关范围分页读取或分批提取。

提取按可复用职责拆分：单个 SkillX 负责一个具有明确输入输出的操作，变化的端口、路径和服务名作为参数；Workflow 组合这些能力和必要判断，并锁定依赖版本。例如端口定位进程、启动日志冲突诊断可作为独立职责，服务诊断则组合它们。能力粒度由独立复用价值决定。

## SkillX 怎样运转

启用 skillx 后，模型侧流程变短：

```text
发现能力名称和说明
→ 读取输入输出契约
→ 准备 JSON 输入
→ 调用 capability_run
→ 使用输出和回执
```

插件内部流程保持完整：

```text
加载能力版本
→ 加载依赖闭包
→ 校验输入
→ 运行执行程序
→ 调用工具或依赖能力
→ 记录事件
→ 校验输出
→ 返回结果
```

外层模型读取根能力的公开契约并调用 `capability_run`，执行程序负责解析依赖和消费中间工具结果。结果字段需要补充核验时，调用方将必要的只读检查合并为一次工具调用。这个分工是效率提升的主要来源。

## 执行程序怎样使用工具

执行程序可以调用 DSH 工具，例如 shell、文件、浏览器或其他已注册工具。调用经过宿主：

- 保留原 Agent、root call 和 execution token。
- 使用当前会话的沙箱策略。
- 工具调用事件写入执行记录。
- 失败会被记录为内部问题、外部阻塞或未知问题。

执行程序也可以调用声明过版本锁的其他 SkillX。这样可以把大任务拆成几个稳定能力，但外层模型仍只看到当前能力的公开契约。

## 恢复怎样工作

恢复分为前台恢复和后台维护。

前台恢复发生在同一次 `capability_run` 内。它读取当前输入、程序、执行轨迹和失败信息，在当前权限和证据范围内补全一个经过 Schema 校验的结果。

后台维护发生在前台失败或超时时。它分析证据、生成诊断，再启动优化任务修订能力定义。

## 为什么启用 skillx 更快

效率提升来自少做重复工作：

| 成本来源 | 未启用 skillx | 启用 skillx |
|---|---|---|
| 能力理解 | 模型读取 Skill 说明和上下文，自行判断步骤 | 模型只读契约 |
| 计划生成 | 每轮重新规划工具顺序和参数 | 已验证步骤在执行程序里固定 |
| 中间状态解释 | 每个工具结果都回到模型上下文继续推理 | 程序内部消费工具结果 |
| 失败定位 | 调用方继续排查 | 插件保留执行记录并分类恢复 |
| 版本复用 | 依赖聊天记录和临时判断 | 依赖不可变版本和回执 |

## 提取与验收

默认提取流程包含职责规划、独立验收契约、实现与修订三个阶段。设置 `contractReview=true` 可在实现前增加契约审查；优化流程使用验收契约、实现与修订两个阶段，也可启用契约审查。各阶段统一使用 SkillX 面板“提取模型”中保存的提供方、模型与推理档位，默认采用 DSH DeepSeek Flash + Low。复杂工作流可选择更高推理档位。配置保存在 `extraction-model.json`，保存后用于新启动的提取与优化任务；任务记录实际配置，来源模型作为证据元信息保留。生成阶段通过工具直接读取字段和提交产物，校验回执驱动局部修订。实现请求直接提供冻结 Schema，提交时由宿主附加到执行契约，模型生成程序。具体用例按需读取，已提供字段纳入读取去重。单次输出被截断，或回合结束仍缺少提交时，宿主在同一会话续写一次，复用已经读取的材料。

验收 Agent 读取证据和工具定义，冻结输入输出 Schema、结果判别条件和声明式用例。实现 Agent 根据冻结契约生成程序；提交失败时依据冻结期望和回执修订实现。默认参数、正常结果、失败和边界需要覆盖，外部操作还需覆盖空结果，依赖调用需覆盖依赖失败。可信的否定或空结果必须与观察失败区分。

验收运行在 macOS 的 `sandbox-exec` 隔离子进程中，工具调用由声明的模拟响应处理。自动故障注入按候选、调用通道和名称、故障类型去重，代表性检查覆盖必要调用异常，以及原生前台命令响应的非零退出、截断和超时，每种调用风险使用代表性用例。请求、输出 Schema 和业务断言全部通过后进入发布流程。

请求断言遵循 SDK 包装：原生工具参数位于 `/arguments`，子能力参数位于 `/input`。冻结前校验断言路径，执行器校验调用参数结构。表示观察失败的空响应同时标记 `empty` 与 `failure`，期望值依据业务契约确定。

模拟验收检查程序对声明响应的处理。候选的核心行为、资源生命周期和环境默认值须具备可核验的依据；证据或验证条件不足的候选通过撤回记录原因。

各阶段成功结束并持久化后，候选批次通过目录事务原子发布。优化保留原实现时，该实现仍须通过当前冻结契约。未启用的优化目标可以保留停用状态，其依赖须启用。

## 跳过提取

职责复用价值或验证条件不足时，提取返回跳过状态，界面显示原因。已有能力覆盖需求时优先复用，新增数量由实际职责决定。

## 提取草稿与预算

### 保存与局部修复

规划、验收和实现草稿保存在 `jobs/<taskId>.<phase>-working-draft.json`，诊断保存为 `jobs/<taskId>.diagnostics.json`。失败或取消后保留草稿；任务状态记录草稿位置、摘要、用量和停止原因。

验收 Agent 用 `upsertContracts`、`finalize:false` 按候选保存，只校验本次 upsert 的候选；最后用 `finalize:true` 校验全部候选并冻结契约。校验一次收集所有可检查问题，返回稳定错误码、候选名、用例 ID 和指向完整草稿的 JSON pointer。诊断过大时返回明确标注的预览，可通过 `read_native_acceptance name=__diagnostics__` 分页获取完整报告。

局部修改先读取 `__draft__` 获取索引和 `draftDigest`，再提交 `draftEdits`（JSON pointer 的 add/replace/remove）；摘要过期则拒绝。实现 Agent 按冻结的验收契约修改已保存候选。完整提交仍兼容。

实现验收失败时，默认反馈失败断言、输出和错误的紧凑摘要。局部修复子 Agent 同时收到失败位置实际使用的模拟响应和故障注入标记，用于定位解析与异常处理问题。子 Agent 的局部补丁经完整候选校验后合并：全部通过，或失败项严格减少且通过项保持通过；剩余问题交给主 Agent 继续修复。完整执行轨迹保存在原始验收回执中，必要时用 `__failures__` 和 `jsonPointer: /results/N/actual/trace` 读取。候选摘要、契约摘要及校验策略均相同的回执可复用；任一变化则重新校验。相同的失败实现再次提交时，宿主返回简短的局部修复提示，并复用已有回执。

### 续跑与成本验证

向 `POST /skillx-workflow/api/extract` 提交 `resumeTaskId` 可复用已有提取的规划、验收草稿和实现草稿。来源任务须已失败、取消或完成，并具有已完成的提取规划。宿主核对来源证据摘要、规划结构和外部依赖版本锁，旧任务及其用量保持独立。

未冻结或摘要不一致的契约重新进入验收阶段。复用冻结契约须满足审查要求，且仍要通过当前工具和依赖契约校验；复用条件与校验结果记录在任务中。已有实现先做隔离校验，只修复失败部分；通过后可用 `useDraft:true` 和当前 `draftDigest` 提交，通过的候选保留已有实现，来源证据继续使用已冻结的记录。

复用草稿进行成本验证时，使用：

```json
{
  "resumeTaskId": "已有提取任务 UUID",
  "validateOnly": true
}
```

验证模式运行模型修复、隔离验收和提交检查，结果保存为任务回执。普通提取的规划优先复用目录中已有能力。

### 上下文与子 Agent

草稿按候选名和具体 `jsonPointer` 读取。整份契约、整份 `cases` 和失败草稿别名只返回索引；字段序列化后超过 10,000 字节时要求下钻。同一阶段内相同字段内容只返回已读引用，阶段切换后按新会话的实际输入重新记录已读内容。来源详情按需分页或分片读取；单批记录超过 64 KiB 时返回索引，供选择更小的详情范围。分片全部交付后才计入已读，已完整交付的同一字段或来源记录再次请求时返回引用。

续跑实现时，宿主一次提供序列化累计最多 32 KiB 的完整引用记录，以及草稿摘要和失败候选字段；未完整提供的引用仍须读取。已有实现的多候选批次中，宿主选择可通过程序修改修复的失败候选，DSH 原生 `spawn` 可用时使用独立上下文的子 Agent。输入包括候选程序、输入输出契约、失败用例的输入和期望、相关请求及诊断。子 Agent 通过结构化输出返回精确的 before/after 替换，宿主校验完整依赖图和该候选的验收结果后合并。每个候选进行一次局部修复尝试；其余候选交由构建 Agent，草稿及被拒绝替换的诊断随任务传递。子 Agent 的模型用量计入任务总用量。

### 预算估算

提取按规划、独立验收、实现串行执行，各阶段共享工作估计；初始时间估计根据来源记录数和字节数计算：

```text
units = max(1, ceil(records / recordsPerBudgetUnit), ceil(bytes / bytesPerBudgetUnit))
budget = min(totalTimeoutMs, maxTimeoutMs, timeoutMs * units)
```

| 配置 | 默认值与作用 |
|---|---|
| `totalTimeoutMs` | 初始总时间估计 10 分钟，运行中自动调整 |
| `timeoutMs` | 每证据单位 10 分钟，用于计算初始估计 |
| `maxTimeoutMs` | 初始时间估计上限 15 分钟 |
| `recordsPerBudgetUnit` / `bytesPerBudgetUnit` | 100 条 / 262,144 字节 |
| `maxSteps` / `maxTotalSteps` | 每阶段 16 步 / 全程 40 步工作估计 |
| `maxTotalTokens` | 初始全程估计 400,000，含缓存读取 |
| `maxOutputTokens` | 全程输出工作估计 64,000 |
| `maxRequestOutputTokens` | 单次请求最多 12,000 输出 Token；局部修复子 Agent 使用相同的单次输出额度 |
| `maxRepairAttempts` / `maxRepeatedFailures` | 修复估计 3 次 / 同一问题连续 2 次；达到阈值时加强局部修复提示 |

提取模型配置见[提取与验收](#提取与验收)。每次请求前，宿主估算输入大小、预留工具 Schema 和单次输出额度，记录剩余额度与预计用量；预计用量超过当前估计时更新估计并继续提取。用户取消、宿主失败和真实模型错误仍正常终止。`GET /skillx-workflow/api/runtime` 可核对实际加载的预算策略。

`GET /skillx-workflow/api/extraction-model` 返回当前提取配置和 DSH 模型目录；向同一路径 `POST` 提交 `provider`、`model`、`reasoningEffort` 保存配置。宿主校验模型和推理档位是否匹配。

## 执行入口与权限

会话内调用 `capability_run` 使用当前调用 Agent 的工作目录和权限。工作台详情页根据输入契约生成表单，锁定所选修订执行，并用幂等键防止网络重试造成重复执行。

工作台直接执行已发布程序，使用宿主进程已有的操作系统权限，未指定工作目录时采用宿主进程工作目录。纯程序使用原生执行上下文，内部 LLM 推理节点按需创建独立对话，并在执行记录中提供入口。工作台执行失败后返回并保存回执。对话内调用继续遵守当前对话权限。

执行记录可查看参数、结果和关联会话。“执行已完成”表示执行流程结束，业务是否成功还须查看输出中的结果状态。

## 删除能力

SkillX 和工作流的列表、详情页均提供删除入口。存在其他现存能力依赖时，删除失败并显示引用者；停用的引用者也参与检查。应先删除引用者或通过优化移除依赖。

删除仅移除当前目录项，历史版本和执行记录仍保留。已经开始的执行继续使用所加载的依赖快照，新执行从当前目录加载能力。发布与删除核对不可变修订 ID，绑定操作对应的条目版本。

## 执行证据与优化反馈

执行记录独立位于监控面板后的“执行记录”选项卡。学习任务可打开当前生成阶段的 DSH 会话；已发布能力可追溯构建会话。运行数据保存在 profile 的插件数据目录中：

- `jobs/`：任务状态、来源 JSONL、职责计划、验收契约及各次验收回执。
- `executions/`：执行头信息、逐步事件和最终回执。

多来源提取与优化以 `sessionIds` 的首个来源作为主来源，记录其原始模型元信息；后续来源可以是纯工具执行会话。各来源的机器执行结果用于证据核验，提取模型由 SkillX 面板配置，当前调用上下文提供权限。

优化 API 的 `reviewFindings` 可提供最多八项、合计 8 KiB 的审查意见。模型将其作为诊断假设，对照证据核实。只读生成阶段提交非法 JSON 时，符合完整捕获等条件的提交允许原模型在当前生成任务内做一次格式修复；该修复的触发条件是宿主已完整捕获并确认提交 JSON 解析失败。
