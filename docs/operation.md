# 运行机制

本页说明 SkillX 在插件中怎样被提取、启用、执行和优化，以及为什么启用 skillx 能减少耗时和 Token。

## 开发者使用路径

```text
完成一次代表性任务
→ 从会话菜单发起 SkillX 提取
→ 等待提取 Agent 生成候选
→ 在 SkillX 页面查看能力
→ 按需启用或停用
→ 后续任务由模型发现并调用 SkillX
→ 用新的执行会话优化能力
```

首次任务仍由 Agent 正常探索。只有当任务结构稳定、执行证据完整时，才适合提取为 SkillX。

## 证据怎样被提取

插件读取 DSH 会话事件，而不是只读聊天文本。证据包括：

| 证据 | 用途 |
|---|---|
| 用户消息和助手回复 | 还原任务目标、输入来源和输出要求 |
| 工具调用和结果 | 还原实际操作、参数、状态和失败点 |
| 未完成调用 | 判断中断或异常边界 |
| step 事件和用量 | 比较耗时、模型调用和 Token |
| turn 结束原因 | 判断会话是否完整完成 |
| 模型请求配置 | 后续提取或优化沿用来源会话模型 |

提取 Agent 必须把历史内容当作证据，而不是当作新指令。它要从证据中总结可复用输入、必要工具、验证条件和失败边界。

证据保存在插件 `jobs/<任务 ID>.source-<序号>.jsonl`，首条提示词只给文件路径、摘要哈希和记录数，不注入对话全文。Agent 通过受限的 `read_native_execution` 工具读取这些固定文件：先分页查看索引或按字面关键词搜索，再读取相关记录；大记录可按字符范围读取局部片段，完整详情则支持分片。所有预览和局部片段都明确标记，不冒充完整证据。工具不接受任意文件路径，也不执行历史指令。

单来源与多来源采用相同机制，不再要求将全部证据依次读入模型。发布记录保留来源 JSONL 哈希及完整读取的记录编号，明确采用选择性审查。每个来源至少完成一次详情读取，只有索引不能提交。提取先保存一个简短职责计划，再经过独立验收契约阶段，由全新 DSH Agent 按计划构建；规划的推理历史不会带入构建会话。计划逐候选引用实际完整读取的 JSONL 记录，构建者必须重新读取对应证据。已有依赖在计划和构建之间锁定版本。发布时检查候选与计划一致，并通过 AST 核对依赖声明和字面名称的 capabilities.run 调用；这仍不能替代业务语义审查或隔离执行验证。缺少证据的候选应省略或说明局限。JSONL 每个文件有 64 MiB 存储保护上限，与模型上下文容量无关。按需读取减少上下文开销，但相关证据本身过大时，仍需缩小范围或分批提取，不能保证任意长度对话一次完成。

提取按可复用职责拆分：单个 SkillX 负责一个具有明确输入输出的操作，变化的端口、路径和服务名作为参数；Workflow 组合这些能力和必要判断，并锁定依赖版本。例如端口定位进程、启动日志冲突诊断可作为独立职责，服务诊断则组合它们。既不把整个来源任务捆成一个专用能力，也不为每条命令生成包装。子工作流仅在有独立复用价值时生成。

## SkillX 怎样运转

启用 skillx 后，模型侧流程变短：

```text
发现能力名称和说明
→ 读取输入输出契约
→ 准备 JSON 输入
→ 调用 capability_run
→ 使用输出和回执
```

插件内部流程保持完整：

```text
加载能力版本
→ 加载依赖闭包
→ 校验输入
→ 运行执行程序
→ 调用工具或依赖能力
→ 记录事件
→ 校验输出
→ 返回结果
```

外层模型读取公开契约，执行程序负责消费中间工具结果。这个分工是效率提升的主要来源。

## 执行程序怎样使用工具

执行程序可以调用 DSH 工具，例如 shell、文件、浏览器或其他已注册工具。调用经过宿主：

- 保留原 Agent、root call 和 execution token。
- 使用当前会话的沙箱策略。
- 工具调用事件写入执行记录。
- 失败会被记录为内部问题、外部阻塞或未知问题。

执行程序也可以调用声明过版本锁的其他 SkillX。这样可以把大任务拆成几个稳定能力，但外层模型仍只看到当前能力的公开契约。

## 恢复怎样工作

恢复分为前台恢复和后台维护。

前台恢复发生在同一次 `capability_run` 内。它读取当前输入、程序、执行轨迹和失败信息，在当前权限和证据范围内补全一个经过 Schema 校验的结果。

后台维护发生在前台失败或超时时。它分析证据、生成诊断，再启动优化任务修订能力定义。

## 为什么启用 skillx 更快

效率提升来自少做重复工作：

| 成本来源 | 未启用 skillx | 启用 skillx |
|---|---|---|
| 能力理解 | 模型读取 Skill 说明和上下文，自行判断步骤 | 模型只读契约 |
| 计划生成 | 每轮重新规划工具顺序和参数 | 已验证步骤在执行程序里固定 |
| 中间状态解释 | 每个工具结果都回到模型上下文继续推理 | 程序内部消费工具结果 |
| 失败定位 | 调用方继续排查 | 插件保留执行记录并分类恢复 |
| 版本复用 | 依赖聊天记录和临时判断 | 依赖不可变版本和回执 |

## 提取与验收

默认提取流程包含职责规划、独立验收契约、实现与修订三个阶段。设置 `contractReview=true` 可在实现前增加契约审查；优化流程使用验收契约、实现与修订两个阶段，也可启用契约审查。各阶段沿用主来源会话的模型配置。

验收 Agent 读取证据和工具定义，冻结输入输出 Schema、结果判别条件和声明式用例。实现 Agent 根据冻结契约生成程序；提交失败时读取回执并自行修订，不能修改验收期望。默认参数、正常结果、失败和边界需要覆盖，外部操作还需覆盖空结果，依赖调用需覆盖依赖失败。可信的否定或空结果必须与观察失败区分。

验收使用 macOS `sandbox-exec` 隔离子进程和模拟工具响应，不执行真实业务工具。必要调用会注入异常、命令非零退出、部分输出、截断和超时；请求、输出 Schema 或业务断言不匹配时不能发布。其他平台目前没有对应隔离后端，无法完成该验收流程。

模拟验收检查程序如何处理声明的响应，不能证明外部系统的实际行为，也不能验证模拟命令生成的外部脚本是否可用。无法验证核心行为的候选应撤回。资源生命周期和环境默认值必须有证据支持；历史回复中的推断不能替代实际观察。

各阶段成功结束并持久化后，候选批次才原子发布。失败、取消或版本冲突不发布部分产物。优化保留原实现时，该实现仍须通过当前冻结契约。未启用的优化目标可以保留停用状态，其依赖须启用。

## 跳过提取

没有稳定、具有独立复用价值的操作，或无法验证候选的核心行为时，可以正常跳过，不发布能力。界面显示跳过原因。提取没有数量目标；已有能力覆盖需求时优先复用。

## 时间预算

提取与优化默认没有步数上限；`maxSteps` 可显式设置限制。时间预算根据全部来源 JSONL 的记录数、字节数和启用阶段数计算：

```text
units = max(1, ceil(records / recordsPerBudgetUnit), ceil(bytes / bytesPerBudgetUnit))
budget = min(maxTimeoutMs, timeoutMs * units * stageCount)
```

| 配置 | 默认值 |
|---|---:|
| `timeoutMs` | 每阶段每单位 30 分钟 |
| `recordsPerBudgetUnit` | 100 条 |
| `bytesPerBudgetUnit` | 262,144 字节 |
| `maxTimeoutMs` | 总计 4 小时 |

小来源默认提取预算为 90 分钟，优化为 60 分钟；启用契约审查时各增加 30 分钟，均受总上限约束。预算在启动前确定，任务可由用户取消。上述参数用于分配预算，不是模型耗时预测。

## 执行入口与权限

会话内调用 `capability_run` 使用当前调用 Agent 的工作目录和权限。工作台详情页根据输入契约生成表单，锁定所选修订执行，并用幂等键防止网络重试造成重复执行。

工作台直接执行已发布程序，使用宿主进程已有的操作系统权限，未指定工作目录时采用宿主进程工作目录。纯程序执行不创建 DSH 对话、不调用模型；仅内部 LLM 推理节点创建独立对话，并在执行记录中提供入口。工作台执行失败保留回执，不自动启动模型恢复。对话内调用继续遵守当前对话权限。

执行记录可查看参数、结果和关联会话。“执行已完成”表示执行流程结束，业务是否成功还须查看输出中的结果状态。

## 删除能力

SkillX 和工作流的列表、详情页均提供删除入口。存在其他现存能力依赖时，删除失败并显示引用者；停用的引用者也参与检查。应先删除引用者或通过优化移除依赖。

删除仅移除当前目录项，历史版本和执行记录仍保留。已经开始的执行继续使用所加载的依赖快照，新执行不能加载已删除能力。发布与删除核对不可变修订 ID，防止误删更新后的条目或覆盖同名重建的能力。

## 执行证据与优化反馈

执行记录独立位于监控面板后的“执行记录”选项卡。学习任务可打开当前生成阶段的 DSH 会话；已发布能力可追溯构建会话。运行数据保存在 profile 的插件数据目录中：

- `jobs/`：任务状态、来源 JSONL、职责计划、验收契约及各次验收回执。
- `executions/`：执行头信息、逐步事件和最终回执。

多来源提取与优化以 `sessionIds` 的首个来源作为模型配置来源；后续来源可以是纯工具执行会话。机器执行结果作为证据保留，不作为新指令。补充来源不会覆盖主来源模型配置或授予权限。

优化 API 的 `reviewFindings` 可提供最多八项、合计 8 KiB 的审查意见。模型将其作为诊断假设，对照证据核实。只读生成阶段提交非法 JSON 时，符合完整捕获等条件的提交允许原模型在原截止时间内做一次格式修复；网络错误或未知执行结果不适用该修复。
