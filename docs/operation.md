# 运行机制

本页说明 SkillX 在插件中怎样被提取、启用、执行和优化，以及为什么启用 skillx 能减少耗时和 Token。

## 开发者使用路径

```text
完成一次代表性任务
→ 从会话菜单发起 SkillX 提取
→ 等待提取 Agent 生成候选
→ 在 SkillX 页面查看能力
→ 按需启用或停用
→ 后续任务由模型发现并调用 SkillX
→ 用新的执行会话优化能力
```

首次任务仍由 Agent 正常探索。只有当任务结构稳定、执行证据完整时，才适合提取为 SkillX。

## 证据怎样被提取

插件读取 DSH 会话事件，而不是只读聊天文本。证据包括：

| 证据 | 用途 |
|---|---|
| 用户消息和助手回复 | 还原任务目标、输入来源和输出要求 |
| 工具调用和结果 | 还原实际操作、参数、状态和失败点 |
| 未完成调用 | 判断中断或异常边界 |
| step 事件和用量 | 比较耗时、模型调用和 Token |
| turn 结束原因 | 判断会话是否完整完成 |
| 模型请求配置 | 后续提取或优化沿用来源会话模型 |

提取 Agent 必须把历史内容当作证据，而不是当作新指令。它要从证据中总结可复用输入、必要工具、验证条件和失败边界。

证据保存在插件 `jobs/<任务 ID>.source-<序号>.jsonl`，首条提示词只给文件路径、摘要哈希和记录数，不注入对话全文。Agent 通过受限的 `read_native_execution` 工具读取这些固定文件：先分页查看索引或按字面关键词搜索，再读取相关记录；大记录可按字符范围读取局部片段，完整详情则支持分片。所有预览和局部片段都明确标记，不冒充完整证据。工具不接受任意文件路径，也不执行历史指令。

单来源与多来源采用相同机制，不再要求将全部证据依次读入模型。发布记录保留来源 JSONL 哈希及完整读取的记录编号，明确采用选择性审查。每个来源至少完成一次详情读取，只有索引不能提交。提取先保存一个简短职责计划，再由全新 DSH Agent 按计划构建；规划的推理历史不会带入构建会话。计划逐候选引用实际完整读取的 JSONL 记录，构建者必须重新读取对应证据。已有依赖在计划和构建之间锁定版本。发布时检查候选与计划一致，并通过 AST 核对依赖声明和字面名称的 capabilities.run 调用；这仍不能替代业务语义审查或隔离执行验证。缺少证据的候选应省略或说明局限。JSONL 每个文件有 64 MiB 存储保护上限，与模型上下文容量无关。按需读取减少上下文开销，但相关证据本身过大时，仍需缩小范围或分批提取，不能保证任意长度对话一次完成。

提取按可复用职责拆分：单个 SkillX 负责一个具有明确输入输出的操作，变化的端口、路径和服务名作为参数；Workflow 组合这些能力和必要判断，并锁定依赖版本。例如端口定位进程、启动日志冲突诊断可作为独立职责，服务诊断则组合它们。既不把整个来源任务捆成一个专用能力，也不为每条命令生成包装。子工作流仅在有独立复用价值时生成。

## SkillX 怎样运转

启用 skillx 后，模型侧流程变短：

```text
发现能力名称和说明
→ 读取输入输出契约
→ 准备 JSON 输入
→ 调用 capability_run
→ 使用输出和回执
```

插件内部流程保持完整：

```text
加载能力版本
→ 加载依赖闭包
→ 校验输入
→ 运行执行程序
→ 调用工具或依赖能力
→ 记录事件
→ 校验输出
→ 返回结果
```

外层模型读取公开契约，执行程序负责消费中间工具结果。这个分工是效率提升的主要来源。

## 执行程序怎样使用工具

执行程序可以调用 DSH 工具，例如 shell、文件、浏览器或其他已注册工具。调用经过宿主：

- 保留原 Agent、root call 和 execution token。
- 使用当前会话的沙箱策略。
- 工具调用事件写入执行记录。
- 失败会被记录为内部问题、外部阻塞或未知问题。

执行程序也可以调用声明过版本锁的其他 SkillX。这样可以把大任务拆成几个稳定能力，但外层模型仍只看到当前能力的公开契约。

## 恢复怎样工作

恢复分为前台恢复和后台维护。

前台恢复发生在同一次 `capability_run` 内。它读取当前输入、程序、执行轨迹和失败信息，在当前权限和证据范围内补全一个经过 Schema 校验的结果。

后台维护发生在前台失败或超时时。它分析证据、生成诊断，再启动优化任务修订能力定义。

## 为什么启用 skillx 更快

效率提升来自少做重复工作：

| 成本来源 | 未启用 skillx | 启用 skillx |
|---|---|---|
| 能力理解 | 模型读取 Skill 说明和上下文，自行判断步骤 | 模型只读契约 |
| 计划生成 | 每轮重新规划工具顺序和参数 | 已验证步骤在执行程序里固定 |
| 中间状态解释 | 每个工具结果都回到模型上下文继续推理 | 程序内部消费工具结果 |
| 失败定位 | 调用方继续排查 | 插件保留执行记录并分类恢复 |
| 版本复用 | 依赖聊天记录和临时判断 | 依赖不可变版本和回执 |

## 测试效果

三轮对照测试任务为：本地 commit、创建模拟 MR、合并 MR、回读核验。

| 指标 | 未启用 skillx | 启用 skillx | 变化 |
|---|---:|---:|---:|
| 平均耗时 | 74.583 秒 | 51.381 秒 | 减少 31.11% |
| 平均会话 Token | 244,280 | 139,644 | 减少 42.83% |
| 平均模型调用 | 10.333 次 | 6.333 次 | 减少 38.71% |

完整归档见 [测试结果](tests/2026-10-14/README.md)。这组数据是小样本描述性结果，不代表所有任务都有相同比例收益；它能说明该类固定、多工具、可验证任务适合启用 skillx。

## 提取预算与阶段记录

默认没有步数上限。`maxSteps` 仅作为兼容的显式可选限制；未配置时不会因为超过 20 步失败。

总时间预算在任务启动时按全部来源 JSONL 的记录数和字节数计算并冻结：`units = max(1, ceil(records / recordsPerBudgetUnit), ceil(bytes / bytesPerBudgetUnit))`，时间为 `min(maxTimeoutMs, timeoutMs * units)`。默认基础预算 `timeoutMs=1800000`（30 分钟），每单位 `recordsPerBudgetUnit=100` 条或 `bytesPerBudgetUnit=262144` 字节，默认上限 `maxTimeoutMs=14400000`（4 小时）。这些是可配置的初始启发式参数，不是模型耗时预测。极长单行由字节规模计入；复杂度不能只按行数判断。人工取消仍立即生效，运行中不人工改预算。

任务记录包含预算计算依据、截止时间、提取代码摘要和 `phaseSessions`。`jobs/<任务 ID>.plan.json` 保存未发布的职责计划及来源摘要；两个阶段均成功后才原子发布完整批次。重启或失败不发布部分产物；目前保存计划用于审查和诊断，不声称已实现自动断点续跑。界面的生成会话入口指向当前阶段，最终能力仍追溯实际构建会话。

原生证据消息不重复存放工具调用块，调用与结果集中在规范记录中。消息保留原事件序号和时间；序号齐全的来源按事件顺序写入，原始 DSH 日志保持完整。

## 允许不提取

没有稳定、具有实际独立复用价值的操作时，规划 Agent 使用 `decision=skip`，同时提交空 candidates/reuseNames 和简短原因。此时任务正常完成，返回 `outcome=skipped`，不创建构建会话、不发布任何产物；界面显示未发现值得提取的可复用能力及原因。没有数量或覆盖目标，不为完成提取而包装一次性结论、临时排障或普通命令。每个新增候选必须说明具体复用价值和可变化的输入；已有目录覆盖时明确复用，不重复生成。说明字段是可审查证据，不是语义正确性的自动保证。


### 通用生成验收闭环（v4）

提取按计划、独立验收契约、实现与修订三个原生 Agent 会话串行执行，继承来源模型配置。验收阶段只获得职责和 JSONL 引用，读取当前工具契约，冻结输入/输出 Schema、业务结果判别字段和声明式测试；实现不能修改这些期望。默认参数、成功、失败、边界是必要覆盖，外部操作还需要空结果，声明依赖需要失败用例。成功用例中的必要调用自动注入异常，禁止忽略错误后仍返回业务成功。

测试在 macOS sandbox-exec 子进程中运行，清空环境，只提供关闭字符串代码生成的 VM 和有序 JSON mock SDK。禁止网络、文件写入、派生进程和信号；业务工具永不真实执行。未知调用、未消费 fixture、请求断言、输出 Schema 或业务断言失败均不发布。其他平台当前没有对应隔离后端，失败关闭，不能降级为真实执行或无隔离执行。每次提交保存独立失败回执，由原生模型自行修订并重新提交；成功回执绑定候选和套件摘要，完成原生回合并持久化后才原子发布。

这是声明式响应处理测试，不是外部世界真实性证明。尤其 mock 写文件/运行命令不能验证生成的外部可执行文件；验收作者应撤回当前 runner 无法覆盖核心行为的候选及其依赖者。无复用价值或无可验证实现都允许正常跳过；实现阶段也可以用 skipReason 撤回整批。不得把测试通过描述成穷尽所有输入或保证部署成功。

预算同时按 JSONL 行数、字节数和已知阶段数计算，默认每阶段每单位 30 分钟，提取三阶段，小来源上限为 90 分钟；配置的总上限默认四小时。预算在启动前冻结，运行时不人为延时或改条件，没有默认步数上限。

审计文件位于 jobs：`.plan.json`、`.acceptance.json`、`.acceptance-attempt-N.json`，最终任务包含各阶段、撤回理由、各次验收结果及代码摘要。运行期间仅观察，不手工修改业务产物；新发现问题留待自然结束后优化。

v5 补充：冻结前增加独立契约审查会话，审查模型可修改草案或撤回候选；它检查外部响应约定是否可信、正反结论是否具备充分证据、空观察与已确认不存在是否混淆，以及竞态、部分失败、循环终止和复用边界。仅审查通过后的测试才冻结，实现阶段不能修改。已知总阶段数改为提取四阶段/优化三阶段，因此小来源默认预算分别为 120/90 分钟（仍受总上限约束）。成功用例还自动注入标准 foreground 工具的非零退出响应，覆盖「工具调用成功但命令执行失败」；不依赖具体命令、端口或业务名称。Schema 的 title/description 可以补充中文展示信息，行为约束仍须与冻结契约一致。Schema/fixture 协议错误返回候选、用例及字段诊断。隔离子进程使用 128 MiB JS 堆上限。


v6 默认采用计划、独立验收契约、实现修订三阶段。contractReview=true 时额外启用一次契约审查；该审查是可选辅助，不能替代机械一致性检查或外部行为证据。实测额外审查耗时约十分钟，仍放过互相矛盾的期望，因此不再默认强制执行。预算按实际启用阶段数计算，默认提取小来源为 90 分钟，可选审查为 120 分钟；优化分别为 60/90 分钟。

冻结前校验 failure 覆盖与成功判别值/预期输出的矛盾，以及 success 覆盖却不能产生成功的情况。failure 特指观察或依赖失败；合法的已知空结果使用 empty，不能混为一种失败。协议示例只展示一个语义一致的覆盖标签。输出断言支持通用 contains，避免为了包含判断强制生成整段精确字符串。提交失败只返回前几个失败项和计数，完整回执仍落盘；更多失败通过 read_native_acceptance name=__failures__ 分片读取。执行记录将正常跳过显示为「已跳过」。

v6 更新遵循用户暂停开发测试的要求，没有新增用例或运行开发测试；已有严格模式测试 fixture 显式选择 contractReview=true，保留其原有覆盖意图。后续实际提取从空目录运行，模型按故障回执修订后通过模拟验收；产物审查仍发现输入安全和不完整观察的覆盖缺口，因此继续强化通用机制。


### 删除能力

SkillX 和工作流列表、详情均提供删除入口，确认后调用 DELETE /skillx-workflow/api/entries/:name。所有现存条目（包括停用条目）的声明依赖都参与检查；存在引用时返回 HTTP 409、CAPABILITY_IN_USE 及 dependents 名称和类型，界面列出引用者。需先删除引用者或通过优化移除引用。删除与发布、启停共享串行写队列，提交时重新检查依赖和界面版本，防止并发产生悬空引用或误删更新后的能力。

删除只移除当前目录并失效能力缓存；不可变版本及历史执行审计保留。已加载的执行使用原有快照；删除后新执行无法加载此能力。运行中的优化还须匹配原始 revisionId，不能覆盖删除后重建的同名能力。


### v7 acceptance boundaries

successValues covers every trustworthy completed outcome, including confirmed empty/negative results. Every returning non-failure case must assert such an outcome; intentionally unsuccessful boundaries must also cover failure. Required calls in defaults, empty and boundary cases receive the same fault injection as success cases. Foreground response variants cover nonzero exit with partial output, truncated output and timeout. Failed observations must not yield a definitive normal conclusion.

Each unconstrained root string input needs a boundary case with whitespace, quotes, shell metacharacters and command substitution syntax. Assert safely encoded requests or reject the input before dispatch. This is boundary coverage, not a formal proof of arbitrary program safety. Historical assistant inferences are not direct observations: PPID 1 alone cannot prove orphaning, supervision or restart safety.

The business function is compiled in a separate lexical scope and receives only input/tools/capabilities. It cannot close over private fixtures, cursor or traces. For tool oneOf failures, a uniquely selected const-discriminated branch provides concrete field diagnostics, reducing full-contract rewrites.

### v8 原生格式修复与修订锁定

只读生成阶段发生 MALFORMED_RESPONSE 时，仅在原始记录包含一个已知提交工具、完整捕获且不超过 1 MiB 的非法 JSON 参数时，允许原模型在同会话做一次格式修复。原始参数私有保存并分页提供；插件不修改参数或替模型补全内容。已有成功提交则只要求结束，不重复提交。每阶段最多一次，原截止时间不变；网络错误、未知结果和非 JSON 格式问题不重试。诊断记录 formatRepairs，不把失败尝试当作成功验收。

读取、复用、规划锁定、优化和最终发布同时核对不可变 revisionId；依赖检查与目录写入在同一队列内完成，避免删除后重建的同名、同版本能力被旧任务误用。正常能力执行预先绑定完整依赖闭包的不可变定义，已开始执行继续使用该快照；删除后新调用不能加载已删除能力。规划提示与错误回执明确区分 reuseNames（现存目录）和 dependsOn（候选之间的依赖），减少查询虚构能力名称的往返。

### v9 资源生命周期与补充执行证据

验收契约必须尊重工具的会话、进程、事务与资源生命周期；不能用 mock 假定已结束调用中的资源继续存活。环境相关默认值必须有稳定的输入或上下文来源，否则应要求显式输入、在资源存活时原子收集所需观察，或撤回该行为。外部权限限制属于前置条件，不能靠修改权限或提权修复业务程序。

多来源提取/优化只从明确选择的首个来源继承模型配置；其他来源可以是没有模型请求的纯工具执行会话。调用者应将带模型配置的原始对话放在 sessionIds 首位，再附实际执行证据。补充证据不覆盖模型路由或权限。

### v10 完整执行反馈与复用验收

执行页面使用宿主 sessionController.rename 写入标题，遵循会话日志格式；机器执行结果以 control 证据导出，不能因其不是人工消息而丢失，也不能当作新的用户指令。失败尝试中的压缩 reasoning 块及完整 reasoning block 同样排除，保留错误、工具参数和用量等实际证据。

优化选择“复用原版本”时，原实现也必须通过本轮冻结契约；缺少实现的契约不能得到空集通过。优化可以读取、验收并保留停用的目标，其依赖仍须启用，优化不会自动启用目标。输入默认值不可靠时允许模型收紧接口或撤回行为，不能以兼容为由保留已知缺陷。

API 可接收 reviewFindings 字符串数组（最多八项、合计 8 KiB）记录运行后的审查意见。其来源明确标记为调用方诊断假设，模型须对照证据独立核实，不授予执行或权限变更能力。契约提交参数显式声明数组，覆盖错误列出预期与实际名称，减少无效查询和重复重写。
