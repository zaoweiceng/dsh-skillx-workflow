# SkillX 介绍

本项目的 SkillX 是运行在 DSH 内的契约化能力。它保留 Skill “按需加载说明”的优点，同时补上程序化调用入口、输入输出 Schema、版本、依赖、权限、副作用和执行回执。

普通 Skill 更像说明书：告诉模型应该怎么做、要读哪些资料、可以运行哪些脚本。模型每次使用时仍需要理解说明、规划步骤、选择工具，并判断输出是否满足要求。SkillX 更像可调用接口：模型只需要判断能力是否适用，按 Schema 提供输入，然后消费经过校验的输出。

## SkillX 解决的问题

| 问题 | 普通 Skill 的典型表现 | SkillX 的做法 |
|---|---|---|
| 上下文成本高 | 使用前常要加载大段说明和参考资料 | 只暴露摘要、Schema 和调用入口 |
| 执行不稳定 | 每次由模型重新规划工具顺序 | 把已验证步骤固化到执行程序里 |
| 边界不清 | 调用方可能重复内部检查或误读中间状态 | 内部实现黑盒化，只返回结构化结果和回执 |
| 难以复用 | 脚本、提示词、人工判断混在一起 | 输入、输出、依赖和版本分开记录 |
| 难以诊断 | 失败后只能看聊天记录 | 保存执行事件、工具调用、失败分类和恢复记录 |

## SkillX 和 Skill 的区别

| 维度 | Skill | SkillX |
|---|---|---|
| 面向对象 | 主要面向 LLM 阅读 | 面向 LLM 发现，也面向运行时调用 |
| 主要内容 | `SKILL.md`、参考资料、脚本 | 说明、Schema、执行程序、依赖、版本和审计 |
| 调用方式 | 模型读说明后自行操作 | 模型调用 `capability_run`，插件执行黑盒能力 |
| 输入输出 | 通常由自然语言约定 | 使用 JSON Schema 校验 |
| 权限边界 | 依赖会话和工具权限 | 使用调用上下文和宿主工具策略 |
| 失败处理 | 调用方继续推理或重试 | 插件先分类，再做受限恢复或返回外部阻塞 |
| 复用粒度 | 复用知识和做法 | 复用已经验证过的执行路径 |

## 本项目里的 SkillX

本插件在 DSH 内把 SkillX 落成可发现、可调用、可审计的能力：

- 提取：用户从一段成功会话发起提取，插件创建新的 DSH Agent 读取证据并产出能力候选。
- 发布：候选必须带名称、说明、输入 Schema、输出 Schema、执行程序和验证说明；生成 Agent 成功结束后才写入插件目录。
- 发现：插件把已启用的 SkillX 注册到 DSH Skill Provider。模型目录里只出现名称和说明。
- 加载：模型选择某个 SkillX 后，获取名称、说明、输入输出 Schema 和调用方式。
- 执行：模型调用 `capability_run`，插件在 DSH PTC 里运行执行程序，期间可以调用工具、锁定版本的依赖能力，必要时调用受限推理。
- 恢复：内部失败优先由插件在同次调用内恢复；权限、凭据、审批等外部问题会返回精简阻塞原因。

## 为什么启用 skillx 能提升效率

启用 skillx 后，模型通过公开契约发现能力、填写输入并消费结果。可复用的固定步骤由执行程序直接跑，模型只负责识别能力、填输入和解释最终结果。

这种收益来自三点：

- 少读：调用方按需读取公开契约。
- 少想：确定性步骤由已发布程序执行。
- 少返工：执行记录、Schema 校验和恢复机制把失败定位放在插件内部处理。

测试归档显示，在同一任务上，启用 skillx 后平均耗时从 74.583 秒降到 51.381 秒，平均会话 Token 从 244,280 降到 139,644，平均模型调用从 10.333 次降到 6.333 次。
