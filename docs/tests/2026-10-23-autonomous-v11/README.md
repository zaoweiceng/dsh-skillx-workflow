# 自主提取与调用实跑 V11

本轮修改集中在 `native-agent.js`、`native-resources.js`、`extraction-reads.js`，不改运行时恢复。没有新增单测，以隔离实跑验证。

## 最小修复

- 证据未读完时，拒绝最终提交必须发生在保存实现草稿之前，避免错误实现先成为后续修改的基准。使用当前摘要可以完整替换草稿；不再把修正限制为结构修补。
- 编写 Agent 可以读取明确记录过的真实源文件；读取与 `resourceSources` 复制共享同一份冻结内容，保留真实参数与结果构造。没有添加文件搜索、额外执行引擎或 CLI 协议。
- 修正草稿字段的失效路径匹配，避免资源字段刚读完又被错误清除。
- 实跑修订时发现 `programEdits` 只能精确修改主程序，资源脚本只能重交大段正文。沿用相同摘要与唯一匹配检查，增加可选 `resourcePath`，只允许修改已有资源文件；不增加修复流程。
- 批量记录超过 64 KiB 不再退化为预览，直接沿用已有无损分页；每页由 10 KB 增至 48 KB，完整读取义务不变，减少模型往返。执行代码和恢复机制不受影响。
- 从已接受计划建立空实现草稿，允许逐步填充。撤回非空实现计划不能被记录成已完成的空交付。

新增的 CLI 调用接口原型未被生成物采用，已撤销；没有修改业务生成物或用运行时恢复替代这些修复。

## 实验口径

同一合成双批次任务、`traex / gpt-5.5 / medium`、同一 Linux 镜像与输入/依赖版本，关闭与开启各一轮。网页提交普通业务描述，没有指定能力名称。Agent 自主提取、调用；失败后的平台原生修订 Agent 自主修改，观察者没有编写生成物。初始提取不计入执行比较，执行失败、修订失败、修订与重跑均计入。

初始提取最终发布六个能力，携带真实审计脚本。脚本存在不代表编排正确，仍按实际调用结果验收。

前期 N11 调试轮遇到挂载源位于输出根内的问题，关闭轮清理输出时破坏了嵌套挂载。该轮不作为最终同环境对比。最终 N12 关闭和开启均将挂载源放在输出根之外，并分别重建同一固定镜像的容器；两边均使用独立新输出根和私有 CLI 安装目录。

N12 关闭轮的 Agent 自编中断控制器阻塞了 Node 事件循环，导致重复等待。观察者发送过一次检查实际进程的进度提醒，没有提供原因或修复代码；Agent 自行诊断并改用 Python 控制器完成。该失败和恢复时间全部计入，因此这一轮耗时不能代表稳定态调用性能。

## 已确认的执行事实

- 普通任务成功自动发现顶层能力，调用 `capability_run`；执行目标沿依赖传入 Linux 容器。
- 首次调用真实进入“验收套件 → 发布审计 → 批次验收 → 数据集能力”三层 workflow，发生并行调用与汇合；回执业务状态为 `failed`，没有被后续单独成功的汇总掩盖。
- 初版数据集 launcher 把 `mode:dataset` 落入 `all`，四个数据集调用实际执行完整套件并共用输出路径，产生 JSON 写入冲突与空汇总。真实脚本复制正确仍不足以保证粒度与调用参数正确。
- 图由执行语法和锁定依赖自动生成，未要求 Agent 编写图元数据。但初版包含固定字符串分类器的并行调用，不能把这部分节点数当作真实业务并行覆盖。
- 初版安装恢复报告标为通过，但中断前证据只有 `.install.lock/owner.json`，不能证明安装文件部分落盘。关闭轮由 Agent 自行补充了真正部分安装的验收；开启轮由平台原生修订 Agent 修改自带脚本中的中断观察条件，工作流自身负责验收，不能调用外补报告。

- N12 修订后 CLI 验收获得真实 `node_modules` 包文件、中断与恢复证据，但核对发现另一处参数丢失：release-b 数据集结果路径仍指向 release-a，两批传入数据集能力的参数相同，缺少批次身份。原生 Agent 随后发布数据集 v3、批次 v3，锁定依赖同步为发布 v3、套件 v6。最终回执的两批数据集报告路径已分别指向各自批次。

## 最终结论与完整成本

**本轮不验收为高效替代方案。** 最终业务回执为 `passed`，但顶层先调用发布工作流，再以 `mode:all` 调用自带资源中的完整审计编排，重复执行原流程；固定字符串分类器的并行调用也不能算实际业务并行。没有从源目录回退执行原程序，也没有调用外补写业务报告，但把完整编排复制到资源里重新执行，仍不满足按粒度拆分并高效复用的目标。不能用最终一次成功调用的成本代替整轮成本。

最终执行回执：`3e9c20c5-1915-40b5-80bc-ad205e444163`。真实调用包含套件 workflow → 发布 workflow → 批次 workflow → 数据集 skill；批次调用两次，数据集调用四次。CSV、图像、模块分支的进程时间区间重叠，汇合生成数据集报告。两批分别为 157 行、117 活动行，金额合计 71625；最终报告路径分属 release-a 和 release-b。批次复用、单分支恢复、损坏产物拒绝复用、失败传播、缺依赖诊断恢复、逻辑错误诊断恢复、四进程 CLI 安装与实际包写入后中断恢复均返回通过；这些局部事实不取消上面的整体不验收结论。

成本根因是遗漏批次参数和错误安装中断观察条件引发反复执行、修订；修订还需重读较大的历史结果与依赖定义，单次数据集修订消耗 2,173,730 Token。当前生成物同时保留分层编排和完整脚本编排，重复责任没有消除，额外分类器调用也没有带来相应业务价值。因此框架可读真实源文件、可修订草稿和资源，只解决信息访问/提交问题，尚不能证明提取粒度及调用语义已经可靠。

本轮不再为这些语义问题添加哈希审计、业务专用静态门禁或运行时兜底。保留最小框架修复，剩余问题如实留在验收结论中；不把生成物返回 `passed` 当作框架已经达成节省 Token 和耗时的证据。
