# 普通任务自主提取与调用：隔离实跑

状态：8 个样本及相关恢复、诊断、修订子会话均结束。当前框架未通过完整验收，不能宣称节约 Token 或耗时。

## 范围

从空能力库提取原始隔离数据发布任务。原生 Agent 自主规划、构建、静态修正、执行和必要修复。观察者仅配置隔离环境、发起普通业务请求和核对证据，不编写或修改生成物，不给执行 Agent 能力名或调用参数模板。开启组调用原始审计程序作为替代入口将记为验收失败，不能当作成功回退。

两组模型均为 traex / GPT-5.5 / medium。相同 Docker 镜像、容器、Python/Node/CLI 版本、输入内容和依赖条件；宿主原始工作目录只读，输入副本和实验输出通过独立挂载可写。原始输入和原始程序保留 SHA-256 基线。正常 3080 实例不重启、不安装依赖。

环境预检：Node 22.23.4、numpy 2.0.2、pandas 2.2.3、pyarrow 19.0.1、sharp 0.34.3、ajv 8.17.1、esbuild 0.25.10。

## 对照口径

三组正常发布审计，各自新会话、新输出，重新计算全部数据集。业务描述、环境说明一致，只有样本标签和输出目录不同。不为关闭组提供完整原始命令，也不为开启组指定能力名。串行顺序为 ON1/OFF1、OFF2/ON2、ON3/OFF3；提取及其模型请求结束后才开始计时样本。

另有一组错误模块的故障恢复任务：两组面对相同的独立错误输入副本，先实际失败，再由 Agent 根据错误修复输入并续跑；成功 CSV/图像分支的报告、产物摘要和 mtime 不应改变。故障数据准备不计入执行，诊断、修复、重试全部计入；独立文件观察器记录实际写入，不以 Agent 自述代替证据。

Token 为完整原生日志中每个 assistant/message 和 assistant/attempt 的未缓存输入、缓存读取和输出之和。仅排除开始执行前的能力提取；执行触发的恢复、诊断、维护和自动修订子会话全部纳入，按会话去重。耗时合并主任务与这些后继工作的活动区间，嵌套时间不重复累加，人工发起间隔不混入执行时间。未结束或用量不完整的后继任务不能给出完整结论。

所有正常样本的非预期失败与恢复保留在对应行。不能通过挑选成功样本、改变任务、放宽正确性或改写产物改善均值。预设故障任务与正常任务分列，不能把更小工作量的失败返回当作加速成功。

## 验收条件

- 普通任务真实自动发现并调用，且没有原程序回退。
- 至少三层实际嵌套；区分 workflow 数量与包括叶子 SkillX 在内的能力层数。能力库最大深度不作为实际执行深度证明。
- 并行有实际分支执行区间重叠，汇合只接受完整业务成功。
- 实际 Parquet 为活动行 group/amount 摘要，PNG 尺寸/像素正确，实际加载 bundle 得到 square(7)=49；批次总数及金额与要求一致。
- 失败不留下成功审计；修复后仅重做失败部分，已有成功分支的产物和报告不重写。

原始证据保存在本机隔离目录 evidence/autonomous-v10；仓库不复制完整私有会话。

## 已确认的失败

首次普通任务确实自动加载公开能力并调用 `capability_run`，但新提取物引用了不存在的 helper 名称。随后 Agent 直接调用原始审计入口；此结果不计为开启组成功。观察者通过平台修订接口提交运行失败事实，原生修订 Agent 自主修改，观察者没有改生成物。普通调用 Agent 没有直接可用的原生修订工具，因此这一阶段不满足完全自主修复。

第一次修订因模型工具 JSON 错误失败；恢复修订后发布 v2，并自动更新上层依赖锁。修订成本纳入 ON1。发布后真实重跑仍失败：helper 名称和 CLI 参数仍与实际外部脚本不同；数据集成功对象把 rows/active_rows 固定为空、金额统计固定为空对象，上层不能完成正确汇合。ON2 自主补外部适配脚本后，已有实际数据产物仍不能让 workflow 生成正确的发布成功结果。ON3 在新会话再次复现不存在 helper 的失败。

完整验收 workflow 的静态内容也不足以证明真实覆盖：环境错误和逻辑错误覆盖项直接赋值 passed；损坏产物项没有实际损坏操作；返回报告路径不等于报告已落盘。这些项目必须以实跑证据判断，不能按发布状态计为通过。

两组共同出现 `TRAEX_INVALID_TOOL_REPLY`，即模型工具响应 JSON 后还有非法内容。失败请求及自动继续目标的全部用量都纳入，不归入 SkillX 独有问题，也不从表格删除。

## 结构、依赖与恢复结论

- 普通业务描述没有给能力名或调用参数模板，四个开启样本都实际发起了 capability_run。自动发现通过；调用成功和成本收益未通过。
- ON4 的实际 implementation/start 回执覆盖：isolated-release-audit-validation-suite → local-release-audit → isolated-batch-acceptance → isolated-dataset-acceptance，即 3 层 workflow 加叶子 SkillX。首个完整套件 runId 为 52eca9d8-acbb-42a4-aa67-b44a26edda9d；不能把前面正常任务的 2 层 workflow 加 SkillX 误称 3 层 workflow。
- 批次和数据集的 native 实现执行区间实际重叠；ON2 图像与模块分支各自报告的时间区间也重叠。并行存在，但业务汇合未通过。实际结构证据见 receipt-structure.json。
- 故障组两边准备的错误模块 SHA-256 相同。关闭组实际遇到 square(7)=14，识别为 script_logic，只修改容器内输入副本后完成发布。观察器跟踪 16 个 CSV/图像产物和报告，均只有一次写入。
- 开启组也自主修复了输入，但观察器跟踪的 48 个 CSV/图像产物中，21 个相同内容文件发生重复写入、mtime 改变，局部恢复失败。不能把相同 hash 当作没有重跑。包括报告共 96 个被观察文件，其中 42 个多次写入。
- CLI 验证器触发 SCRIPT_OUTPUT_INVALID 后，系统自主诊断并修订该依赖；新的失败返回契约不等于并发安装与中断恢复成功，本轮不能将此场景判为通过。
- 新提取物将自身引用的 JS helper 缺失归类为 environment_missing_dependency，实际是提取物脚本契约错误；环境问题与代码问题的区分未通过。
- 普通故障任务自动选中了完整套件，额外执行 CLI/预检等场景，说明提取粒度和候选入口仍会带来额外工作。故障行保留这部分自动选择成本，不是等量内部操作的微基准。

## 干预与协议变更

观察者没有编辑任何生成的 manifest、程序或资源；ON2 的适配脚本及 ON4 的额外最终核验报告均为 Agent 自行编写，不能据此视为框架已修复。第一次运行后的修订由观察者调用平台接口触发，内容完全由原生作者完成，未实现无需外部触发的完整自主修复。ON4 的诊断、持久修订与上层依赖更新则由框架自行触发，其全部成本计入 ON4。

首次提示未明确写出“禁止原程序回退”，但已要求不换实现掩盖失败；第一次回退保留为失败。之后两边提示均补充相同的条件式禁止回退要求，没有提供能力名、参数模板或修复代码。也同时明确允许原入口自身写入容器内实验专用 setup 报告与日志。所有提示与变更均有本机记录。

## 下一步最小修复位置

应先修提取提交交付链：让提取物保留真实业务脚本及其参数契约，业务实现随能力携带，避免把 scriptsDir 变成让调用者补实现的入口。其次收敛结果：将真实分支结果映射为上层可用的简洁统计对象；失败对象、成功对象、报告存在性不能混同。最后用同一业务验收核对提交物的实际输出，避免空统计和未经执行的 passed 覆盖项被发布。继续加发现提示词、手改生成物或用运行时恢复包装结果，均不能解决这次的根因。

本轮未改框架、未新增或运行单测；实跑前后 13 个受保护原始文件、30 个冻结框架源文件 SHA-256 全部相同。
