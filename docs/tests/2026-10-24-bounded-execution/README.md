# 调用成本根因与有界实跑

这是本机隔离实验，不是公开性能基准。目标是同任务调用更快、Token 更少；提取成功、静态发布与 DAG 层数均不能替代真实验收。

## 已确认的旧轮次原因

同一复杂审计任务原始执行为 327.398 秒、637,163 Token；失败的 SkillX 轮次为 7,788,364 Token，活动区间合并为 2,931.827 秒。其 4,384.967 秒首尾跨度另含观察与等待间隔，不能全算执行耗时。后续诊断、修订和重跑占 6,557,143 Token（84.19%）；98.74% 为输入及缓存读取，反复扩大上下文比输出代码本身昂贵。

1. 根工作流读取与子结果不一致的字段路径，把子验收通过结果改判失败。例如将嵌套 module 分支的 squareResult 当作 afterRecovery 的直接字段读取。
2. 新增显式修订入口只传外层会话和文字 findings，没有传失败 runId 的原始能力边界输入、执行契约与输出；连续多次修订子验收，未消除根聚合错误。
3. 验收只能调用较大的发布职责，且重跑使用随机新目录。12 次根调用累计执行 52 次完整发布；更新依赖锁被当成实现已修复，继续重跑。
4. 对话连续性保留了大量历史，但没有解决重复诊断与无效重跑；主会话输入从 23,348 增长至 161,664 Token。

早期约 16 秒、6.8 万 Token 的正向表格来自不同的 Git/mock-MR 任务，不是该复杂任务在旧提交上的对照，不能据此断言代码版本退化倍数。

## 本轮最小修复

- 原生显式修订要求失败 runId；作者按需读取保留的真实输入、输出及执行契约，普通调用方也能只读查询能力边界索引。
- 修订回执区分实现修改与依赖锁更新。
- 规划不再要求过早确定公开 Schema，构建依据原始脚本完成；允许补充来源支持的小操作依赖，不能删掉规划中必要职责。
- 原始 CLI 返回契约明确为 exitCode 与 stdout.text，避免错误读取业务 status 或 stdout 字符串。

没有手工修生成物，没有运行时业务 Agent 兜底，没有添加单元测试。CLI Schema 在真实启动中发现宿主 DSL 不支持 required 数组，已按宿主写法修正；语法、diff 与修改文档的本地链接检查通过。

## 验证口径

模型均为 TraeX / gpt-5.5 / medium，固定 Linux 镜像、只读原始源码和输入，专用容器及输出目录。普通任务描述不指定能力名，禁止回退原始完整入口；必须由 workflow 完成最终报告。

仅做一轮调用比较。初次提取单独统计；调用计入主 Agent 与修订作者的全部 inputTokens + cacheReadTokens + outputTokens，并计失败及恢复。原始轮次 A14-OFF-1，新的有界轮次 B16-ON-1；相同任务文本仅修改轮次标记与新输出根。

验证专用外部观察器从原生 turn/start 计时，读取本轮及修订作者的原生日志用量；达到 637,163 Token 或 327,398 毫秒时限即停止私有服务和专用容器。模型用量在请求结束结算，因此 Token 取消可能存在单次请求超额，不宣称逐 Token 的硬截断。该限制只用于本次实验，不加入生产框架。

完整原始本机证据保存在隔离实验 evidence/bounded-v16，初次提取任务 1a747aef-eb4d-43b7-90cd-0824401e0268。不复制会话原文作为公开基准。

首次提取另耗 445.888 秒、966,870 Token，未计入上表。Agent 自主发布 9 个能力。普通任务完成自动发现，发起 1 次 capability_run；观察者未手改生成物，也未回退完整原始入口。

调用前发生 18 次 glob，至首次 capability_run 耗时 79.147 秒。公开根接口仍强制调用者提供 8 个业务/环境路径。来源脚本原有 PY、NODE_ROOT、ESBUILD_ROOT 默认指向既有 dag-v2 运行时，提取包装将其替换为必填参数；调用方未发现这些固定默认值，改为新输出根的环境。nodeRuntimeRoot 同时存在“私有前缀根目录”与“node_modules 目录”的含义歧义。

三个并行分支各自调用 runtime-prepare，共观察到 6 次相同运行环境准备；首批并发创建同一 venv 报 File exists，其后反复 pip 安装。批次程序未在前一个数据集阻塞后及时返回，继续进入后续数据集。到达上限时仍未完成正常发布，没有进入完整故障验收，不能声称三层嵌套、并行汇合或局部恢复已通过。

这次修复改善了原始证据可达性与进程返回契约，但没有解决固定运行配置被过度参数化、共享准备职责被下沉到每个分支的问题。完整执行中未走到修订作者读取新边界证据的环节，因此该通路也尚未获得端到端实跑确认。不能将本次变更标为 P0 完成；按本轮上限停止，不继续追加同任务修订和重跑。

下一步最小修复应围绕来源配置与编排职责：保留实际成功执行中的固定默认配置，只把用户需要变化的值暴露为输入；共享环境准备在并行分叉前完成，并将已准备结果传给分支。不能用对任意 capability_run 自动缓存或去重来掩盖该问题，后者会改变有副作用能力的调用语义。


## 后续框架修复与复验

停止预算耗尽的轮次不代表停止修复。随后解除规划依赖位置的强制锁定，保留身份/职责及真实调用校验；调整固定运行配置的默认值要求。B17 普通任务无需路径搜索，但因父输入透传字段不符合子 Schema，实际修订 4 次后仍在 Token 上限停止：活动 201.080 秒、643,025 Token（结算后超额）。该失败轮次不计为优化成功。

继续补齐可静态确定的依赖字段检查、业务 outcome 未消费检查；嵌套输入失败保留拒收边界并记录参数组装方 repairTarget，显式修订据此指向真实调用方，原子重锁父级。草稿先保存为未验证状态，再检查缺失来源引用，发布条件不放宽。

同口径任务中的“该目录/.venv”存在歧义，已在关闭与开启两侧同步改为沿用源码已成功使用的配置。新原始基线 B18-OFF-1 已完成 7 项验收、目标已 complete：229.061 秒、691,976 Token，含首次未改输出目录的失败尝试与目标收尾。原始副本仅改变 HERE，没有改业务逻辑。模型用量在结束结算时跨过旧 Token 上限，观察器随即停止私有服务，结算前业务与目标收尾已完成。后续开启侧上限取更严格的 229.061 秒和 637,163 Token。

静态发布的 v18 生成物在只读检查中发现“子能力预检查 + 原始 all 入口”的重复执行，未用于通过性实跑；没有手改生成物。随后框架加入相关 outcome 消费检查，并让原生 Agent 从新基线会话自主重新提取。后续结果待实跑核验。

## 严格验收纠正与持续修复

以上 B18 完整通过结论已撤回：B18 与 v21 的安装中断验收只在中断前记录到 `.install.lock/owner.json`，没有证明真实包文件已经落盘。原脚本的 passed 条件不足，因此两次都不能作为完整七项通过的比较。v21 已有普通描述自动发现及一次 capability_run 的真实记录，主 Agent 为 72,827 Token；暂不据此计算完整任务节省率。

观察器停止超限测试，不停止框架根因修复。隔离原生 Agent 负责修正私有验收源码；关闭与开启侧必须使用同一修正后的来源。源码准备与初次提取单列，调用比较计入失败及作者修订。P22 准备首轮因模型响应格式故障及超时未完成；后续继续成本另行保留，不覆盖此前记录。

框架补齐实际脚本函数的构建期适配，保持原始业务函数体和已有 JSON 调用协议，避免 Agent 重写业务导致实现丢失。固定来源配置保留默认值；修订保留原始成功来源，并将嵌套参数拒收指向真正组装参数的调用方。可静态确定的依赖调用在同一次提交中同时报告缺少必填字段、多余字段与丢弃失败 outcome，动态表达式仍由原运行契约检查。没有增加运行时业务兜底。

P22 的私有 CLI 验收最终由原生 Agent 修复并实际通过：中断前 esbuild 包文件与二进制存在、ready 不存在，进程组 SIGKILL 后使用原安装器恢复，CLI 实测版本 0.25.10。只读对比确认业务函数未改变。源码准备不是调用性能收益，不计入最终调用对比。

B22 原始执行侧也因 TraeX 工具响应格式错误反复结束，尚未进入正常业务，因而不能成为基线。根因是宿主桥接的格式修复通路撤掉工具并强制输出最终报告。宿主 `llm-traex` 已改为只纠正未派发的下一条响应，保留原工具定义，沿用每步至多一次重试；已执行工具不回放。派发检查只允许经过解析校验的替代响应，不再把合法格式修正也一律禁止。该变更与 SkillX 业务恢复分离，两侧都必须重启私有进程加载相同桥接实现。原 3080 服务未重启。

后续还确认了两项干扰：混合“说明文字 + calls JSON”会被当普通回答，调用实际未派发；旧隔离工作区可被搜索到历轮历史报告，导致原始侧上下文膨胀。前者改为显式格式错误，后者用全新工作区排除，不能把清理环境的收益算给 SkillX。B24 原始业务七项实际通过，但 Agent 收尾在 205.702 秒、已结算 643,263 Token 时被保守上限终止，不能伪造完整成本。

文本协议对大型提交仍会出现格式错误，因此宿主桥接改用 CLI 原生 output-schema：外层只有 calls 与 text，工具名受限，参数作为 JSON 字符串传输并在派发前解码为原工具参数对象。业务契约未改；结构错误不会作为最终回答吞掉。失败的提取从保留草稿继续，不手工编辑生成物。对比两侧必须加载同一个结构化桥接版本，前述旧桥接轮次仅保留为失败实验。

## B29：停止失败测试后继续修复

严格 CLI 验收与结构化桥接统一后的有效原始基线为 B26-OFF-1：203.051 秒、677,705 Token，14 次用量结算，正常发布与全部七项故障验收完成。后续仅修改能力编写与诊断通路，因此复用该基线，不重复执行无关的原始侧。

B29 普通描述自动发现根能力并调用。真实正常 DAG 的四个 CSV 分支误用了通用 `python3`，而相同容器中的来源程序使用已有虚拟环境；图像、模块及归档源验收函数通过不能证明提取后正常 DAG 已完成。根、发布、批次与数据集还存在只返回报告路径、未落盘或省略原聚合检查的问题，不能用验收套件的 passed 掩盖。

本轮观察到的框架放大因素及最小修复：

- `executionReview.summary` 无基础设施异常时仍包含 `failure: undefined`。业务失败诊断因此被宿主整个拒绝，调用者收到 `value is not lossless JSON`，丢失可用运行编号并重新扫描、重跑。改为仅构造实际存在的可选字段。用真实失败执行记录读取九个边界，已通过原宿主的 lossless JSON 检查。
- 无效边界 ID 或字段只返回错误码，调用者多次猜测。返回结构化错误及可直接使用的只读 `read` 请求；真实记录的两种错误均已验证可以按回执读到原始边界索引，没有业务重执行。
- 修订作者读取整边界时，重复携带所有嵌套子结果和命令日志。完整结果保留，整边界输出采用明确标注的不完整预览并提供精确字段读取；该真实根结果由 73,533 字节降为 2,099 字节。输入与执行契约保持完整。这是传输体积结果，不是完整任务 Token 节省率。

B29 首次调用在 203.450 秒触发停止，已结算 547,205 Token；取消时存在未完成调用，成本为下界，不作为优化通过样本。停止该次测试后继续修框架，并由原 Agent 通过原生修订处理生成实现，没有手改生成物。单独保留后续开发修订成本，不能当作调用节省。

后续原生批次修订曾因 `TRAEX_EMPTY_ANSWER` 结束，发布层又因该批次尚未更新而遇到传递依赖版本冲突；均未算作修订成功。宿主桥接将未派发任何工具的空响应接入已有的每步一次格式纠正，不增加重试层，也不回放已执行工具；上游有用量时先结算再返回空响应错误，避免将该失败的成本丢失。仅修改空响应分支，正常响应路径保持一致。定向 TypeScript 构建通过；空响应恢复是否实际触发须以原生日志为证，不能凭构建宣称验证完成。

### B30/B31 的进一步根因

B30 在 165.520 秒、717,733 Token 的结算点停止，包含实际原生修订，未完成；Token 按请求结束结算而超额。其关键框架原因是 `executeProgram` 无条件以根级目标覆盖子调用显式传入的解释器，且资源启动继续使用全局目标。父程序正确派生私有 Python 也无法生效。修复为调用作用域内继承、传递解释器配置；容器及宿主 Docker 客户端保持同一执行边界，不修改并行分支共享状态。B31 原生记录已确认 CSV 子能力实际使用私有虚拟环境并执行成功。

B31 随后因数据集返回 `started_at`、`finished_at` 未列入其输出 Schema 被拒收。旧记录在验证之前写入 `implementation/end`，导致作者看到“completed”却在父级收到 `OUTPUT_SCHEMA_INVALID`。现在记录真实验证错误并保留原输出；旧记录复核也依据原契约判定，回执给出实际产出方及字段错误，不靠反复猜测父节点。

同轮还观察到模型将 `<tool-call ...>` 放进回答文本，桥接当普通最终文本收下，真实修订未发生，目标继续执行后误以为已修订并重跑旧版本。桥接现在拒绝这种回答形态并使用已有的一次格式纠正；不把文本标签直接执行成工具。B31 在 179.780 秒、690,824 Token 结算点停止，未完成，不能计算节省率。此后的生成修订及验证继续保留独立证据。

### 修订成本与错误归因闭环

B32 正常发布真实通过，但 JSON 资源脚本在故意缺失依赖时返回了 `undefined`。原始进程观测记录退出 1 及 `SCRIPT_OUTPUT_NOT_JSON`；脚本调用却直接解析空 stdout，误报 `SCRIPT_OUTPUT_INVALID`。JSON main 模式现在先检查进程结果，再解析输出并保留脚本 marker；原 CLI argv 模式仍返回原始退出结果。类型化宿主错误在能力边界记录中保留，父程序捕获异常后仍可定位真实资源与产出方。B32 在 203.747 秒、738,294 Token 结算点停止，未完成。

另一个放大因素是基于真实失败做局部修订仍被强制重读每个原始提取会话，以及没有改变的子能力全文。现在有已发布实现和真实执行复核的 optimize 不强制重读整段历史；仅在锁定版本与修订 ID 均未改变时复用已发布依赖证明。首次提取及改变的依赖仍按原要求读取，静态契约校验不取消。同一资源的两次相近缺失字段修订，原生作者分别为 9 步 / 79.109 秒 / 628,248 Token 与 2 步 / 20.552 秒 / 85,891 Token；它们修复不同字段，仅作为成本来源证据，不当作严格性能基准。

### B33 最终单轮通过

本机实验条件：TraeX / gpt-5.5 / medium；同一 Linux AArch64 固定镜像、只读输入与原始源码、相同既有 Python/JS 依赖；每轮全新输出根和专用容器。普通描述不指定能力名。原始侧复用已完整结算的 B26 基线；后续桥接只修改错误响应路径，没有改变该基线实际经过的正常响应路径。结果是一轮样本，不代表统计稳定的普遍收益。

| 修复后单轮完整任务 | 203.051 秒 | 79.350 秒 | 677,705 | 137,658 |
