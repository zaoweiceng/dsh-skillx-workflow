## 框架改动与原因

- 源码与原调用上下文：定位相对脚本路径及分号分隔的字面量变量；源码接口提供调用位置、参数表达式及公共 CLI 环境覆盖项。函数适配保留原始初始化表达式，`bindings` 仅在明确传值时覆盖；不再把解释器、库目录等所有绑定强制变成必填。void 函数转 JSON null，保留目录准备等原始副作用。没有新增运行时自动建目录、自动安装或自动恢复。
- 参数与返回：构建时根据实际透传关系补齐对象的子契约，减少调用者继续读取内部能力；检查可静态确定的返回对象是否漏掉 Schema 必填字段。动态表达式仍受原有运行时输出验证约束。
- 复用语义与副作用：根据真实源码入口及 argv 拒绝组合子能力后重放原始完整任务；检查独立 CLI 是否保留原父调用共同提供的环境覆盖。本例为 INSTALL_TRACE，遗漏它会把安装日志写进只读依赖前缀。
- 诊断：目标内 cwd 不存在时返回明确目录诊断；经 PTC 捕获的脚本失败保留简短原始信息，避免调用方只看到 `SCRIPT_PROGRAM_FAILED:0` 后修错执行目标。

业务代码未写死进框架，没有增加内容哈希门禁、新执行 DSL、额外 OS 实现或运行时补救机制。未新增单测，以真实原始作业和新能力实跑验收；对前一轮真实草稿直接调用构建检查，确认能识别原来的 8 处输出/调用环境问题。对 C36 真实生成物确认能识别完整入口重放。

编译行为标识更新为 `esm-functions-v2`，说明与诊断已同步到 operation.md。实跑后仅补齐该标识和 validationReceipt 的检查名称，不改变执行行为。已有发布资源不自动重编译，需重新提取；本轮没有修改存量能力。

## 真实结构与恢复证据

实际调用路径为：根归档 → 双批发布 → 单批发布 → 数据集并行校验 → 三个叶子 SkillX，共四层 workflow。执行回执中，数据集 workflow 和三个叶子各实际调用 4 次，批次 workflow 调用 2 次。三种业务资源进程存在共同重叠时间段，数据集汇合进程在三者结束后启动。见 execution-dag-proof.json。

DAG 由当前程序与锁定依赖自动生成，Agent 没有编写图：静态图 24 节点、26 边；有一个动态并行区域不能静态确定成员。该不确定性保留在图中，实际嵌套及重叠由运行记录证明，不将静态图当作运行证据。
